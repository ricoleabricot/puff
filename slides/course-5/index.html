      Staying up is not keeping up

      High availability

      The service stays up when one piece breaks

      Scalability

      It keeps up when more people show up

      A bakery staying open when a cashier is sick, versus serving a hundred people at once.

        A bigger server, or more of them?

        Scale up

        A bigger server. No code change, but a ceiling and a restart on every resize

        Scale out

        More servers behind a load balancer. No real ceiling, availability for free, the app must run as several copies

        Scaling out is what the cloud is good at, and it only works if your servers are disposable.

          The ALB hides a sick server, the ASG gets rid of it

          Load balancer check Auto Scaling check (type ELB)
          Who decidesThe ALBThe ASG, trusting the ALB
          When a server failsVisitors stop going to itIt's thrown away and replaced
          Fixes the problem?No, it walks around itYes, a fresh server takes its place

          Keep /health shallow. Deep checks belong in monitoring, where they raise an alarm.

            What an Auto Scaling group needs

            • A launch templateThe recipe for one server: AMI, size, security group, instance profile, user data
            • Three numbersmin never fewer, max never more (your cost ceiling), desired right now
            • Subnets in different AZsOne data center goes dark, the other half keeps running
            • A scaling policyTarget tracking: "keep average CPU around 50%" and AWS adds or removes servers

              Puff already works this way

              Your servers have to be stateless

              The group can terminate any server at any time. No uploads on disk, no sessions in memory, no SQLite file. State goes to RDS, S3 or a cache.

                    One building down, or the whole city?

                    Multi-AZ

                    The normal setup for anything real. RDS keeps a twin in another AZ, switches in a couple of minutes, same address

                    Multi-region

                    Data copied hundreds of km away, DNS sends users to the right place, the whole stack exists twice

                    RDS Multi-AZ means paying for two databases to use one, like a spare tire.

                      Write it in your project justification

                      puff-db is your single point of failure

                      The sandbox blocks Multi-AZ RDS. If its AZ goes down, every API server returns errors.
