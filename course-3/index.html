📖 Words you'll meet today
  • VPC (Virtual Private Cloud): your own private network inside AWS, closed to the outside by default.
  • CIDR block: an IP range written as a start address plus a size, like 10.0.0.0/16.
  • Availability Zone (AZ): one of the separate data centers inside an AWS Region.
  • Subnet: a slice of your VPC's IP range that lives in one AZ.
  • Route table: the list of rules that tells traffic leaving a subnet where to go next.
  • Internet Gateway (IGW): the two-way gate between your VPC and the internet.
  • NAT gateway: a one-way exit that lets private servers go out without anyone coming in.
  • Security group: a firewall attached to one server (or load balancer, or database) that only lists who is allowed in.
  • Network ACL (NACL): a firewall attached to a whole subnet that checks traffic in both directions.
  • VPC endpoint: a private path from your VPC to an AWS service, without going through the internet.
  • ALB (Application Load Balancer): the public front door that receives web requests and passes them to healthy servers.
  • Target group: the list of servers a load balancer sends traffic to, with a health check.

🧱 The VPC: your own private network

In last session, your database had a public address, so anyone on the internet could try to connect, and only a password stopped them.
A private network solve this problem.

A VPC (Virtual Private Cloud) is a private network in one Region, and it spans all of that Region's Availability Zones (AZs, the separate data centers inside a Region).
Nothing gets in unless you open a way in, like a gated neighborhood where you draw the streets and build the gates.

The default VPC you used in last session has public subnets everywhere, so things work on the first try.
That's also why your database ended up public, and a real app needs the opposite.

When you create a VPC you give it a CIDR block (Classless Inter-Domain Routing, a way to write an IP range as an address plus a size).
Puff uses 10.0.0.0/16.

  • /16 means the first 16 bits are fixed (10.0) and the last 16 are yours, so 2\^16 = 65,536 addresses, from 10.0.0.0 to 10.0.255.255.
  • You then cut it into subnets. A /24 like 10.0.1.0/24 holds 256 addresses, and you can fit 256 of those in the /16.
🔍 Want more? Reserved addresses and size limits
  • AWS keeps 5 addresses in every subnet: the network address (.0), the VPC router (.1), the DNS resolver (.2), one reserved for later (.3) and the last one (.255 in a /24). So a /24 gives you 251 usable IPs.
  • A VPC can be anywhere from /16 (largest) to /28 (16 addresses, 11 usable).

Puff's wizard creates 10.0.0.0/20 and 10.0.16.0/20 as public subnets, and 10.0.128.0/20 and 10.0.144.0/20 as private ones.
Each /20 holds 4,096 addresses, far more than Puff needs, and private IPs cost nothing.

The range matters even on a private network, because one day you'll connect it to something else (a second VPC, an office, a VPN).

A packet for 10.0.3.7 must have one home only, so AWS refuses to connect overlapping VPCs.
Fixing that later means rebuilding the network and moving every server in it.

⚠️

Common collisions: home routers on 192.168.0.0/24 or 192.168.1.0/24, Docker's default bridge on 172.17.0.0/16, and a lot of corporate networks somewhere in 10.0.0.0/8.

Picking 10.0.0.0/16 for a course is fine.

In a company, ask whoever owns the IP plan before you create anything.

🏢

Real-world corner: at Alan, a health insurance company that runs on AWS, we use several AWS accounts, and networks that may need to talk get non-overlapping IP ranges, decided before the network exists, because changing a range later takes weeks.

🛣️ Public vs private subnets

This decides whether a server can be reached from the internet, so it's the idea to get right today.

A subnet is a slice of the VPC's range that lives in exactly one AZ, like a street in the neighborhood.
You create them in pairs across AZs, so losing one data center doesn't take your tenant down.

There's no "public" checkbox on a subnet, its route table decides.

  • A subnet is public when its route table (the list of rules that says where traffic goes next) sends 0.0.0.0/0, meaning "everything outside the VPC", to an Internet Gateway.
  • It's private when it doesn't.

Every route table also has a local route for the VPC's own range, so subnets in the same VPC can always reach each other (firewalls then decide if they're allowed to).

DestinationPublic route tablePrivate route table
10.0.0.0/16locallocal
0.0.0.0/0igw-... (Internet Gateway)nat-... (NAT gateway)
S3 prefix list pl-...vpce-... (endpoint)vpce-... (endpoint)

To find out whether a subnet is public, don't trust its name, open its route table and look at where 0.0.0.0/0 goes.

To be reachable from the internet, an instance also needs a public IP.
The board app's API will have neither a public IP nor a public subnet.

🔍 Want more? Which route wins

When several routes match a destination, the most specific one wins. A packet for 10.0.3.7 matches both 10.0.0.0/16 and 0.0.0.0/0, and the /16 is more specific, so it stays local. That's also why an S3 endpoint's prefix list beats the 0.0.0.0/0 route for S3 traffic.

🚪 Internet Gateway and NAT gateway: the two doors

Your private API still needs to download Docker, the python:3.12-slim image and OS updates.
You need a way out that isn't a way in.

The Internet Gateway (IGW) connects your VPC to the internet.
Traffic goes both ways and can start from either side, there's one per VPC and it's free.

The NAT gateway (Network Address Translation) is a one-way exit.
It sits in a public subnet with an Elastic IP (a fixed public address you keep).

  • Private subnets send 0.0.0.0/0 to it.
  • It swaps the sender's address for its own public IP, and it only lets replies come back.
  • Nothing on the internet can ever start a conversation with your private API through it.

The map uses plain names, the zones are AZs, the one-way exit is the NAT gateway, the load balancer is puff-alb, the server is puff-api and the database is puff-db.

Puff's network spans two AZs, with one public and one private subnet in each.
The public subnets hold the ALB and the NAT gateway, the private subnets hold the API and the database.
The public route table sends everything leaving the VPC to the Internet Gateway, the private one sends it to the NAT gateway.

A visitor comes in through the Internet Gateway, then the ALB, then the API, and the API talks to the database.
A download goes the other way, from the API to the NAT gateway, then the Internet Gateway, then Docker Hub, and the reply comes back the same way.
A stranger gets stopped, because the API has no public IP and its subnet has no way in from the internet.

A NAT gateway charges per hour and per GB.
In us-east-1 that's about $0.045 per hour (roughly \$32 a month doing nothing) plus $0.045 per GB processed.

⚠️

The NAT gateway is a classic surprise on a cloud bill, it keeps charging while you sleep.

In the sandbox, delete it at the end of the lab session if you don't need it.
In real life always ask "does this traffic need to go through the NAT at all?", often it doesn't (see VPC endpoints below).

Puff still takes one, because without it the private API can't install Docker or pull the image, and the health check never goes green.

You could put the API in a public subnet "with a strict security group" instead, but then one wrong rule exposes it, while a private subnet has no way in whatever the rules say.
So we pay for one NAT.

🔍 Want more? One NAT or one per AZ, and how bills grow
  • With a single NAT, if its AZ goes down, the private instances in the other AZ lose outbound access. Puff can live with that. A system that depends on outbound calls would pay for one NAT per AZ.
  • The per-GB fee comes on top of normal data transfer. A team that runs one NAT per AZ in three AZs, in dev, staging and prod, pays for nine gateways before a single byte moves.
  • An app that pulls large images or backs up to S3 through the NAT can turn the per-GB line into the biggest network item on the invoice.

🛡️ Security groups vs network ACLs

Routes decide where traffic can go, firewalls decide who's allowed through, and you'll touch them every day you work on a cloud.

A security group is a firewall on one resource (an instance, a load balancer, a database), like a bouncer with a guest list.
It only has "allow" rules, and it remembers who it let in, so replies go out automatically, that memory is what "stateful" means.

A network ACL (Access Control List) is a firewall on a whole subnet.
It reads numbered rules from the lowest up, first match wins, and it can allow or deny.
It has no memory ("stateless"), so replies need their own rule.

Security groupNetwork ACL
Applies toOne server's network cardA whole subnet
MemoryRemembers, replies get out automaticallyNo memory, replies need their own rule
RulesAllow onlyAllow and deny
How it reads rulesAll at once, any match lets you inIn number order, first match wins
DefaultNew group: nothing in, everything outDefault NACL: everything allowed both ways
When you use itEvery dayRarely, as an extra layer or to block one IP range

Security groups do 95% of the work.
Leave NACLs at their default unless you have a precise reason (like blocking an abusive IP range), because stateless rules are easy to get wrong and painful to debug.

🔍 Want more? Why stateless rules bite

If a NACL allows inbound 443, you also need an outbound rule for the ephemeral ports (1024 to 65535) the replies go back to. Forget it and the request arrives, the server answers, and the answer gets dropped at the subnet edge. From the outside it looks like a timeout, which is the hardest kind of bug to read.

💡

The best security group rules don't mention IPs at all.

A rule can say "allow port 5432 from anything that has security group puff-api-sg", and it still holds when you add a second API instance or an IP changes.
That's security group chaining, and it's how we lock Puff down.

Puff's chain:

Security groupInbound ruleSource
puff-alb-sgTCP 800.0.0.0/0
puff-api-sgTCP 8080puff-alb-sg
puff-db-sgTCP 5432puff-api-sg

Read it from the bottom: the database only talks to the API, the API only to the load balancer, and only the load balancer talks to the world.
A stranger can only reach port 80 on the ALB.

If your first connection test fails later today, one link of this chain is missing, and finding it is the best way to learn this table.

🕳️ VPC endpoints: a private path to AWS

Reaching S3 from a private server through the NAT costs money per GB, for a service sitting in the same Region.

A VPC endpoint is a private path from your VPC straight to an AWS service.
A gateway endpoint exists for S3 and DynamoDB only, it's a line in the route table (destination: the service's prefix list, target: vpce-...), it's free, and S3 traffic stops touching the NAT.

A private instance that copies 500 GB of backups to S3 each month through the NAT pays about \$22 in NAT processing for nothing.
Add the S3 gateway endpoint to the private route table and that line drops to zero, with no change to the application.

Puff gets the free S3 gateway endpoint from the wizard.

🔍 Want more? Interface endpoints

For most other AWS services there's the interface endpoint (also called PrivateLink). It puts a network card with a private IP in your subnet. It's billed per hour per AZ and per GB, so you add one when the traffic, or a rule that says "never leave the private network", justifies it.

🔗 Connecting networks

One VPC isn't enough forever, a second app arrives, or a company keeps its payroll database in its own building.
Four tools link networks, from small to big.

  • VPC peering: a private connection between two VPCs. Free to set up, routes on both sides, and it doesn't chain (A peers with B, B with C, A still can't reach C).
  • Transit Gateway: a central hub every VPC and VPN connects to once, like a roundabout.
  • Site-to-Site VPN (Virtual Private Network): an encrypted tunnel over the internet to an office router. Up in an hour.
  • Direct Connect: a private physical cable from a data center into AWS. Takes weeks to set up.
SituationUseWhy
Two or three VPCs need to talkVPC peeringSimple and free, the "doesn't chain" limit doesn't hurt yet
Ten VPCs across accounts, plus an officeTransit GatewayOne connection per network instead of a web of links, one place for routing
Office needs access to AWS this weekSite-to-Site VPNFast to set up, encrypted, cheap
A data center sends terabytes to AWS every day, or needs steady speedDirect Connect (with VPN as backup)Predictable speed and cheaper data transfer at volume

None of these works with overlapping ranges, so the IP plan is what keeps all four options open.

🔍 Want more? The four tools in detail
  • Peering works across accounts and Regions, you pay only for data, and it refuses overlapping ranges.
  • Ten VPCs that all need to reach each other with peering means 45 separate peering connections. A Transit Gateway replaces that web with ten attachments, and its route tables decide who talks to whom. It's billed per attachment per hour and per GB.
  • A VPN is cheap, but its speed and latency depend on the internet. Direct Connect gives stable latency and cheaper data at volume for a fixed monthly fee, and big companies often keep a VPN as its backup.

⚖️ Load balancers: the only public door

Once the API is private, something public has to receive visitors and pass them to it.

A load balancer receives the traffic, spreads it across your instances and skips the unhealthy ones, like a receptionist sending visitors to free desks.
Later, it lets Puff add instances behind one stable address.

It has three parts:

  • Listeners: the port it accepts, for example HTTP 80.
  • Target groups: the instances it forwards to, with a health check.
  • Rules: they connect the two.
🔍 Want more? ALB or NLB
Application Load Balancer (ALB)Network Load Balancer (NLB)
What it understandsWeb traffic (HTTP and HTTPS), layer 7Raw connections (TCP, UDP, TLS), layer 4
How it routesBy path, host name, header, query stringBy port only
AddressA DNS name, the IPs behind it changeA DNS name with one fixed IP per AZ
ExtrasHandles HTTPS certificates, redirects, loginVery fast, keeps the visitor's real IP
Pick it forWeb apps and APIs (the board app)Non-web protocols, fixed IPs a partner can allowlist, huge traffic

AWS has two main kinds, the ALB (Application Load Balancer) for web traffic and the NLB (Network Load Balancer) for raw connections.
For anything that speaks HTTP, start with an ALB.
Use an NLB when you need a static IP or a protocol the ALB doesn't speak.

An ALB must sit in public subnets in at least two AZs to receive internet traffic, and its targets can sit in private subnets.

🧪 Hands-on: Build a VPC by hand

This one is a course lab: Module 7 guided lab, creating a Virtual Private Cloud (FR: « Atelier guidé : création d'un cloud privé virtuel (VPC) »).
You build a VPC piece by piece: subnets, an Internet Gateway, a NAT gateway, route tables, a security group, and an instance to test it.

This is the slow, manual version of what the wizard does for you in the sandbox.
Doing it once by hand makes the wizard's output readable later, so take your time on the route tables.

While you do it, look at this:

  • When you create a subnet, nothing about it says "public". It becomes public the moment you associate it with a route table that points 0.0.0.0/0 at the IGW. Check the subnet's Route table tab before and after.
  • The NAT gateway goes in a public subnet but serves the private route table. Put it in the private subnet and nothing gets out.
  • The NAT's Elastic IP is what the outside world sees for every private instance, handy when a partner asks "which IP should we allowlist?"
  • Look at the local route in each table. You never created it and you can't delete it.
  • Only the NAT gateway (and its public IPv4) costs anything while idle.
✅

How you know it works: the lab's test instance in the private subnet can reach the internet outbound (the lab's ping or curl test succeeds), and in VPC > Route tables you can point to the one route that makes each subnet public or private.

🧪 Hands-on: Peering two VPCs (optional)

This one is a course lab too: Module 8 guided lab, creating a VPC peering connection (FR: « Atelier guidé : création d'une connexion d'appairage de VPC »).
You build a peering connection between two VPCs, with routes on both sides, so an app in one VPC can use a database in the other.

It's homework if we run late.
It's short, and the clearest way to see why non-overlapping ranges matter.

While you do it, look at this:

  • Compare the two VPC ranges first. If they overlapped, the console would refuse.
  • A peering connection alone does nothing until you add a route on each side to the other VPC's range through pcx-....
  • Security groups must also allow the other VPC's range (or, within one Region, a security group from the peered VPC).
  • A third VPC peered with the second stays unreachable from the first. That "doesn't chain" rule is why Transit Gateway exists.
✅

How you know it works: the lab's test (an app in one VPC querying a database in the other) succeeds, and you can name the two routes that make it possible.

🧪 Hands-on: Puff's private network

This part happens in the sandbox.
You build Puff's private network, puff-vpc, with public and private subnets in two AZs.
Your tenant moves in: the API in a private subnet with no public IP, a fresh puff-db in private subnets, a chain of three security groups, and puff-alb as the only public door.
The frontend on S3 now calls the ALB.

Start the sandbox (Start Lab, green dot, click AWS), check you're in us-east-1, and keep the browser terminal open in a second tab.

  1. Free the puff-db name first. RDS names are unique per Region and deleting takes several minutes, so start now and let it run while you build the network. Course 2's messages are test data, nothing to lose.
aws rds delete-db-instance \
  --db-instance-identifier puff-db \
  --skip-final-snapshot \
  --delete-automated-backups

Keep the old puff-api instance running for now. You'll terminate it at the end, once the new one works.

🔍 Want more? Keeping your data instead

If you wanted to keep the data: take a snapshot (RDS > Databases > puff-db > Actions > Take snapshot), delete the old instance, then Snapshots > Actions > Restore snapshot into the new DB subnet group with the new security group. Same user and password, same data, new network. We create a fresh database instead because it's quicker and the API recreates its table on boot.

  1. Create the VPC with the wizard. Open VPC > Your VPCs > Create VPC and choose VPC and more.
  • Name tag auto-generation: puff (the wizard names things puff-vpc, puff-subnet-private1-us-east-1a, and so on).
  • IPv4 CIDR block: 10.0.0.0/16, no IPv6.
  • Number of Availability Zones: 2.
  • Number of public subnets: 2. Number of private subnets: 2. Keep the default /20 ranges.
  • NAT gateways: In 1 AZ.
  • VPC endpoints: S3 Gateway.
  • DNS options: keep both Enable DNS hostnames and Enable DNS resolution checked.

Look at the preview before clicking Create VPC, it draws the route tables we just saw. The NAT gateway takes a few minutes to become available.

🔍 Want more? The same network with the CLI

The wizard runs roughly these calls. You don't need to run them, but reading them shows every piece the wizard hides.

VPC_ID=$(aws ec2 create-vpc --cidr-block 10.0.0.0/16 \
  --tag-specifications 'ResourceType=vpc,Tags=[{Key=Name,Value=puff-vpc}]' \
  --query Vpc.VpcId --output text)
aws ec2 modify-vpc-attribute --vpc-id $VPC_ID --enable-dns-hostnames

PUB1=$(aws ec2 create-subnet --vpc-id $VPC_ID --cidr-block 10.0.0.0/20 --availability-zone us-east-1a --query Subnet.SubnetId --output text)
PUB2=$(aws ec2 create-subnet --vpc-id $VPC_ID --cidr-block 10.0.16.0/20 --availability-zone us-east-1b --query Subnet.SubnetId --output text)
PRIV1=$(aws ec2 create-subnet --vpc-id $VPC_ID --cidr-block 10.0.128.0/20 --availability-zone us-east-1a --query Subnet.SubnetId --output text)
PRIV2=$(aws ec2 create-subnet --vpc-id $VPC_ID --cidr-block 10.0.144.0/20 --availability-zone us-east-1b --query Subnet.SubnetId --output text)

IGW_ID=$(aws ec2 create-internet-gateway --query InternetGateway.InternetGatewayId --output text)
aws ec2 attach-internet-gateway --internet-gateway-id $IGW_ID --vpc-id $VPC_ID

EIP_ALLOC=$(aws ec2 allocate-address --domain vpc --query AllocationId --output text)
NAT_ID=$(aws ec2 create-nat-gateway --subnet-id $PUB1 --allocation-id $EIP_ALLOC --query NatGateway.NatGatewayId --output text)
aws ec2 wait nat-gateway-available --nat-gateway-ids $NAT_ID

PUB_RT=$(aws ec2 create-route-table --vpc-id $VPC_ID --query RouteTable.RouteTableId --output text)
aws ec2 create-route --route-table-id $PUB_RT --destination-cidr-block 0.0.0.0/0 --gateway-id $IGW_ID
aws ec2 associate-route-table --route-table-id $PUB_RT --subnet-id $PUB1
aws ec2 associate-route-table --route-table-id $PUB_RT --subnet-id $PUB2

PRIV_RT=$(aws ec2 create-route-table --vpc-id $VPC_ID --query RouteTable.RouteTableId --output text)
aws ec2 create-route --route-table-id $PRIV_RT --destination-cidr-block 0.0.0.0/0 --nat-gateway-id $NAT_ID
aws ec2 associate-route-table --route-table-id $PRIV_RT --subnet-id $PRIV1
aws ec2 associate-route-table --route-table-id $PRIV_RT --subnet-id $PRIV2

aws ec2 create-vpc-endpoint --vpc-id $VPC_ID --vpc-endpoint-type Gateway \
  --service-name com.amazonaws.us-east-1.s3 --route-table-ids $PRIV_RT $PUB_RT

The wizard creates one private route table per AZ (both pointing at the same NAT), where this outline uses one shared table. Both work.

  1. Grab the IDs you'll need. In the browser terminal:
VPC_ID=$(aws ec2 describe-vpcs --filters Name=tag:Name,Values=puff-vpc \
  --query 'Vpcs[0].VpcId' --output text)

aws ec2 describe-subnets --filters Name=vpc-id,Values=$VPC_ID \
  --query 'Subnets[].[Tags[?Key==`Name`]|[0].Value,SubnetId,AvailabilityZone,CidrBlock]' \
  --output table

Note the two public and two private subnet IDs. Then open VPC > Route tables, select a private route table and check its Routes tab: 0.0.0.0/0 goes to nat-... and there's a pl-... entry for the S3 endpoint.

  1. Create the three chained security groups.
ALB_SG=$(aws ec2 create-security-group --group-name puff-alb-sg \
  --description "Puff ALB, HTTP from the internet" --vpc-id $VPC_ID \
  --query GroupId --output text)
API_SG=$(aws ec2 create-security-group --group-name puff-api-sg \
  --description "Puff API, only from the ALB" --vpc-id $VPC_ID \
  --query GroupId --output text)
DB_SG=$(aws ec2 create-security-group --group-name puff-db-sg \
  --description "Puff DB, only from the API" --vpc-id $VPC_ID \
  --query GroupId --output text)

aws ec2 authorize-security-group-ingress --group-id $ALB_SG \
  --protocol tcp --port 80 --cidr 0.0.0.0/0
aws ec2 authorize-security-group-ingress --group-id $API_SG \
  --protocol tcp --port 8080 --source-group $ALB_SG
aws ec2 authorize-security-group-ingress --group-id $DB_SG \
  --protocol tcp --port 5432 --source-group $API_SG

In EC2 > Security Groups, open puff-db-sg: the inbound source is a group ID, not an IP. No SSH rule anywhere, on purpose.

  1. Create the DB subnet group and the database. Wait until step 1's deletion has finished (aws rds describe-db-instances --db-instance-identifier puff-db returns DBInstanceNotFound), then:
aws rds create-db-subnet-group \
  --db-subnet-group-name puff-db-subnets \
  --db-subnet-group-description "Puff DB in private subnets" \
  --subnet-ids <private-subnet-1a-id> <private-subnet-1b-id>

aws rds create-db-instance \
  --db-instance-identifier puff-db \
  --engine postgres \
  --db-instance-class db.t3.micro \
  --allocated-storage 20 --storage-type gp2 \
  --db-name puff \
  --master-username puff \
  --master-user-password '<choose-a-password>' \
  --db-subnet-group-name puff-db-subnets \
  --vpc-security-group-ids $DB_SG \
  --no-publicly-accessible \
  --no-multi-az \
  --backup-retention-period 1

RDS > Subnet groups > Create DB subnet group, then RDS > Databases > Create database with Standard create, PostgreSQL, db.t3.micro, storage type gp2, VPC puff-vpc, subnet group puff-db-subnets, Public access No, security group puff-db-sg (remove default), initial database name puff, enhanced monitoring unchecked.

The subnet group needs two AZs even for a single-AZ database, hence the two private subnets. Creation takes 5 to 10 minutes. Then get the endpoint:

aws rds describe-db-instances --db-instance-identifier puff-db \
  --query 'DBInstances[0].Endpoint.Address' --output text
  1. Launch puff-api in a private subnet. Open EC2 > Instances > Launch instance.
  • Name: puff-api. AMI: Amazon Linux 2023. Type: t3.micro. Key pair: vockey.
  • Network settings > Edit: VPC puff-vpc, subnet puff-subnet-private1-us-east-1a, Auto-assign public IP Disable, select existing security group puff-api-sg.

The user data runs as in course 2, except every download now leaves through the NAT gateway. Without it, this step fails silently and the instance sits there with no container.

  1. Create the target group and the load balancer.
TG_ARN=$(aws elbv2 create-target-group --name puff-api-tg \
  --protocol HTTP --port 8080 --vpc-id $VPC_ID --target-type instance \
  --health-check-path /health --health-check-interval-seconds 15 \
  --healthy-threshold-count 2 \
  --query 'TargetGroups[0].TargetGroupArn' --output text)

API_ID=$(aws ec2 describe-instances \
  --filters Name=tag:Name,Values=puff-api Name=vpc-id,Values=$VPC_ID Name=instance-state-name,Values=running \
  --query 'Reservations[0].Instances[0].InstanceId' --output text)

aws elbv2 register-targets --target-group-arn $TG_ARN --targets Id=$API_ID

ALB_ARN=$(aws elbv2 create-load-balancer --name puff-alb \
  --type application --scheme internet-facing \
  --subnets <public-subnet-1a-id> <public-subnet-1b-id> \
  --security-groups $ALB_SG \
  --query 'LoadBalancers[0].LoadBalancerArn' --output text)

aws elbv2 create-listener --load-balancer-arn $ALB_ARN \
  --protocol HTTP --port 80 \
  --default-actions Type=forward,TargetGroupArn=$TG_ARN

The instance query filters on the new VPC because your old course 2 instance is also called puff-api.

🧯 If it doesn't work
  • Target shows unhealthy in EC2 > Target groups > puff-api-tg > Targets: give it 3 to 4 minutes after launch (Docker install plus image build). Still unhealthy? Check puff-api-sg allows 8080 from puff-alb-sg and the health check path is /health, not /.
  • No container ever starts: look at EC2 > Instances > puff-api > Actions > Monitor and troubleshoot > Get system log. Timeouts on dnf or docker pull mean no outbound path: check the private route table has 0.0.0.0/0 to nat-... and the NAT gateway state is Available.
  • Health is ok but /api/messages returns 500: the API can't reach the database. Check DB_HOST in the user data, puff-db-sg allows 5432 from puff-api-sg, and the database status is Available.
  • You need a shell on the private instance: EC2 > Instances > puff-api > Connect > Session Manager works without SSH or a public IP (course 4 explains how).
  • create-db-instance says the identifier already exists: the old puff-db is still deleting, wait.
  • RDS rejects the password: avoid /, @, " and spaces.
  • curl to the ALB hangs: puff-alb-sg is missing the port 80 rule, or you put the ALB in private subnets.
  • Lab session expired in the middle: restart the lab, the resources you created should still be there.

🤔 Think about it

  • A second team builds an analytics VPC that needs to read puff-db, and an office needs access to both. Which tools would you pick, and what choice from today could make this impossible?
  • Your NAT gateway line on the bill doubled this month. Name two kinds of traffic that could cause it, and how you'd take each one off the NAT path.

💡 Hints
  • Route table (is the destination local?), then the security group on each end, then the NACL. Same VPC means routing is already fine.
  • Think about what stops traffic when a rule is wrong: in a private subnet there's no route in at all, so a bad rule changes nothing.
  • Peering or Transit Gateway for VPC to VPC, VPN or Direct Connect for the office. Overlapping CIDRs kill every option.
  • S3 traffic (gateway endpoint), traffic to other AWS services (interface endpoints), image pulls (cache or pull less often).
  • The load balancer is designed to survive one AZ failing, your one instance isn't. Course 5 adds an Auto Scaling group across both AZs.
