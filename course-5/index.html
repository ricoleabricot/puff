📖 Words you'll meet today
  • HA (high availability): the service keeps answering when one piece breaks.
  • AZ (Availability Zone): one or more data centers in a region, with their own power and network.
  • ASG (Auto Scaling group): a group of identical servers that AWS keeps at the right number for you.
  • Launch template: the recipe AWS follows to build one more server for the group.
  • Health check: a small request the load balancer sends every few seconds to ask a server "are you OK?".
  • CDN (Content Delivery Network): copies of your files kept close to users all over the world. On AWS it's called CloudFront.
  • TTL (time to live): how long a cached copy counts as fresh before it must be fetched again.
  • Lambda: AWS's service that runs one function when an event happens, with no server for you to manage.
  • Serverless: you hand AWS code, AWS runs it when needed, and you pay only while it runs.
  • Queue (SQS): a waiting line for messages, so the sender doesn't wait for the receiver.
  • Orchestrator: software that starts, restarts and spreads containers over machines (ECS, Kubernetes).
  • Stateless: a server that keeps nothing important on itself, so losing it loses nothing.

⚖️ High availability vs scalability

These two words come up in every project defense, and people mix them up.

  • High availability (HA) means the service stays up when one piece breaks,
  • Scalability means it keeps up when more people show up.

Like a bakery, staying open when a cashier is sick is one thing, serving a hundred people at once is another.

Two servers in two AZs (Availability Zones, separate data centers) give you availability even if traffic never changes.
One giant server gives you some scalability and zero availability, when it dies everything dies.

  • Vertical scaling (scale up): a bigger server.
  • No code change, but there's a ceiling and every resize means a restart.
  • Horizontal scaling (scale out): more servers behind a load balancer.
  • No real ceiling and availability comes for free, but your app must run as several copies at once.

If your single puff-api server from course 4 crashes during a demo, the board is dead until someone notices.
With two servers behind puff-alb, nobody sees a thing.

Horizontal scaling is what the cloud is good at, and it only works if your servers are disposable.

🚦 Load balancing, the recap

You built puff-alb (your ALB, Application Load Balancer) in course 3.
It sends each visitor to one of the healthy servers of puff-api-tg, like a receptionist sending people to a free desk.

Every few seconds it calls GET /health on each one, and a server that keeps failing gets no more visitors.
With today's Auto Scaling group, that failing server also gets replaced.

The ALB hides a sick server, the Auto Scaling group gets rid of it, and you want both.

🔍 Want more? Two kinds of health checks, and keep them shallow
Load balancer health checkAuto Scaling health check (type ELB)
Who decidesThe ALBThe Auto Scaling group, trusting the ALB's verdict
What happens when a server failsVisitors stop being sent to itThe server is thrown away and replaced
Does it fix the problem?No, it walks around itYes, a fresh server takes its place

If /health also queried the database, one slow query could mark every server unhealthy at the same moment and take the whole site down, even though the servers were fine.
The board app's /health answers from the process itself, and that's the right default.
Deep checks ("can I reach the database, the cache, the payment provider?") belong in monitoring, where they raise an alarm instead of pulling servers out.

📈 Auto Scaling

Today a crash means you, at 2 a.m., starting a new server by hand.
With Auto Scaling, AWS does it for you.

An Auto Scaling group (ASG) keeps the right number of servers running, it adds some when load grows and removes some when it's quiet, like a supermarket manager opening checkouts when the line grows.
It needs three things:

  • A launch template: the recipe for one server.
  • Its AMI (Amazon Machine Image, the disk it boots from), plus size, security group, instance profile and user data.
  • Three numbers: min (never fewer), max (never more, so also your cost ceiling) and desired (how many right now).
  • A list of subnets in different AZs, so if one data center goes dark the other half keeps running.

A scaling policy moves desired between min and max.
Today you use target tracking, you say "keep average CPU (how busy the processor is) around 50%" and AWS adds or removes servers to stay there.

💡

Your servers have to be stateless.

The ASG can terminate any instance at any time, so nothing that matters lives on it, no uploads on local disk, no user sessions in memory, no SQLite file.
State goes to RDS, S3 or a cache.

Puff already works this way, that's why scaling it today takes a few commands and no rewrite.

🔍 Want more? Three kinds of policies, grace periods and scale-in
Target trackingStep scalingScheduled scaling
You say"Keep average CPU around 50%""If CPU > 70% add 1, if > 90% add 3""At 08:00 on weekdays set desired to 6"
Who sets up the alarmsAWS, for youYou, in CloudWatchNo alarms, a clock
Good forMost web appsSpiky traffic where you want precise reactionsKnown rush hours
DownsideLess control over how fast it reactsMore settings to get wrongBlind to surprises

Start with target tracking on one metric, and use step scaling only when you can show a graph where target tracking reacted badly.

  • A new server has to boot, run its user data, pull the Docker image and pass health checks, which takes minutes. The health check grace period tells the group to wait, so it doesn't kill a server that's still starting.
  • Scaling in (removing servers) is slower on purpose, around 15 minutes of low load, to avoid flapping (adding and removing servers back and forth every minute).
  • Scheduled scaling combines with the other two. A shop that knows Black Friday is coming hires extra staff the night before instead of waiting for the line.

🏛️ Multi-AZ and multi-region

Data centers do lose power, so Multi-AZ is the normal setup for anything real.
For servers that's your ASG across two AZs, you'll do it today.

For the database, RDS Multi-AZ (RDS is AWS's managed database service) keeps a twin in another AZ that receives every write.
If the main one dies, RDS switches to the twin in a couple of minutes, at the same address.
You pay for two databases to use one, like a spare tire.

⚠️

The sandbox blocks Multi-AZ RDS, so puff-db stays single-AZ.
That's the single point of failure in your design, if its AZ goes down all your API servers return errors.

Write it down for the project justification, a jury likes a student who knows where their architecture breaks.

Multi-region protects you when a whole region fails, and it's a much bigger step.
Your data is copied hundreds of kilometers away, DNS (the internet's phone book) sends users to the right place, and your whole stack exists twice.

🏢

Real-world corner: at Alan, a health insurance company, production runs in AWS Frankfurt (eu-central-1) across several AZs, and backups are copied to Paris and to a separate AWS account.

The separate account matters as much as the second region, if a stolen password can delete the backups you have no backups.

🔍 Want more? Active-passive, active-active, RPO and RTO
🅰️

Active-passive

One region serves everyone.

A second region holds a copy of the data and either a small idle stack or only the recipe to rebuild it. On disaster, DNS switches over.
Cheaper, but a backup plan you never rehearse tends to fail on the day you need it.

🅱️

Active-active

Both regions serve users all the time, so surviving a failure means "stop sending people to the broken one".

Fast to recover and tested every day by real users, but writing the same data in two places at once is hard and expensive.

Two numbers drive the choice.
RPO (Recovery Point Objective) is how much data you can afford to lose, counted in time, "RPO 1 hour" means losing the last hour of messages is acceptable.
RTO (Recovery Time Objective) is how long you can afford to be down.

🧭 Route 53 routing policies

Route 53 is AWS's DNS service, when someone types a name it answers with an address.
It can pick the address with a rule: the healthy region, the fastest region for this user, or the user's country.

The sandbox can't register a domain, so you'll only see these in the Module 10 demos.

Latency routing is about speed, geolocation is about rules (law, licensing, language), and they can give different answers for the same user.

🔍 Want more? The five routing policies and the DNS cache trap
PolicyWhat it doesExample for Puff
SimpleOne name, one answerpuff.example.com points to puff-alb
FailoverMain answer while it's healthy, backup answer otherwiseFrankfurt ALB first, a static "we'll be back" page on S3 as backup
LatencySends each user to the fastest region for themUsers in Montreal go to ca-central-1, users in Paris to eu-west-3
GeolocationSends users by country or continentFrench users go to the EU stack because of data residency rules
WeightedSplits users by percentage90% to the current version, 10% to the new one (a "canary")

Browsers and phones remember DNS answers for the record's TTL, so with a 300 second TTL some users keep hitting the dead region for up to five minutes after you switch.

⚡ Caching: CloudFront and friends

A cache answers requests before they reach your servers, so pages load faster and your servers do less.

CloudFront is AWS's CDN (Content Delivery Network), it keeps copies of your files in hundreds of places called edge locations, in front of your origin (an S3 bucket, a load balancer, any web server).
Like corner shops in every city, so customers don't have to drive to the factory.

  • Cache hit: the edge has a fresh copy and answers in milliseconds.
  • Cache miss: it fetches from the origin and keeps a copy. The X-Cache response header tells you which.
  • TTL: how long a copy stays fresh, 24 hours by default.
  • Invalidation: you ask CloudFront to throw its copies away early, useful after a deploy.

You fix a typo in index.html and upload it to S3.
The S3 website URL shows the fix right away, the CloudFront URL still shows the typo for up to 24 hours.

CloudFront also gives you HTTPS (the padlock in the browser) on a *.cloudfront.net name for free.

🔍 Want more? Cache-Control, versioned files, ElastiCache and a privacy trap
  • If you cache a response holding personal data without the user in the cache key, the next visitor sees someone else's page. Cache content that's the same for everyone first.
  • The TTL comes from the origin's Cache-Control header, kept within the minimum, default and maximum you set on CloudFront.
  • Versioned file names (app.3f9a.js) beat invalidations: new content gets a new URL that no edge has cached yet, so there's nothing to throw away.
  • ElastiCache (managed Redis-compatible or Memcached) is the other kind of cache, in memory, between your API and the database. With the cache-aside pattern, the API checks the cache first, and on a miss reads RDS and stores the result with a TTL. Caching GET /api/messages for 2 seconds would cut database reads a lot during a busy class and nobody would notice. It's not in the sandbox, so keep it for your project justification.

🧪 Hands-on: Puff scales itself

This part happens in the sandbox.


You build puff-api-lt, an Auto Scaling group puff-asg (min 2, desired 2, max 4) in your two private subnets behind puff-api-tg and a CPU target tracking policy, then you prove that it heals and scales.

⚠️

The sandbox suspends your account above 9 running instances.

Today you'll have up to 4 ASG instances plus anything left from earlier courses.
Count before you start (step 1) and terminate the old puff-api instance at step 6. Never raise max above 4.

  1. Open the sandbox (Start Lab, wait for the green dot). In the browser terminal, set your variables and count your running servers:
export AWS_DEFAULT_REGION=us-east-1
LOGIN=yourlogin   # lowercase, same as your bucket name

aws ec2 describe-instances \
  --filters Name=instance-state-name,Values=pending,running \
  --query 'Reservations[].Instances[].[InstanceId,Tags[?Key==`Name`]|[0].Value]' \
  --output table

Terminate any stray server from earlier tests now.

  1. Grab what you need from the course 4 server: its AMI, security group and user data. Reusing its user data means the new servers read the database password from Parameter Store exactly like before.
API_ID=$(aws ec2 describe-instances \
  --filters Name=tag:Name,Values=puff-api Name=instance-state-name,Values=running \
  --query 'Reservations[0].Instances[0].InstanceId' --output text)
AMI_ID=$(aws ec2 describe-instances --instance-ids $API_ID \
  --query 'Reservations[0].Instances[0].ImageId' --output text)
API_SG=$(aws ec2 describe-instances --instance-ids $API_ID \
  --query 'Reservations[0].Instances[0].SecurityGroups[0].GroupId' --output text)

aws ec2 describe-instance-attribute --instance-id $API_ID --attribute userData \
  --query 'UserData.Value' --output text > userdata.b64

echo $API_ID $AMI_ID $API_SG
base64 -d userdata.b64 | head -20

The last command should print your course 4 script. If it's empty, paste that script into userdata.sh and run base64 -w0 userdata.sh > userdata.b64.

  1. Create the launch template. Detailed monitoring sends CPU numbers every minute instead of every five, so scaling reacts within class time. No key pair, you've used Session Manager since course 4.
cat > lt.json <<EOF
{
  "ImageId": "$AMI_ID",
  "InstanceType": "t3.micro",
  "IamInstanceProfile": {"Name": "LabInstanceProfile"},
  "SecurityGroupIds": ["$API_SG"],
  "UserData": "$(cat userdata.b64)",
  "Monitoring": {"Enabled": true},
  "TagSpecifications": [
    {"ResourceType": "instance", "Tags": [{"Key": "Name", "Value": "puff-api-asg"}]}
  ]
}
EOF

aws ec2 create-launch-template --launch-template-name puff-api-lt \
  --launch-template-data file://lt.json \
  --query 'LaunchTemplate.LaunchTemplateId' --output text
  1. Find your two private subnets and the target group:
VPC_ID=$(aws ec2 describe-vpcs --filters Name=tag:Name,Values=puff-vpc \
  --query 'Vpcs[0].VpcId' --output text)
PRIVATE_SUBNETS=$(aws ec2 describe-subnets \
  --filters Name=vpc-id,Values=$VPC_ID "Name=tag:Name,Values=*private*" \
  --query 'Subnets[].SubnetId' --output text | tr '\t' ',')
TG_ARN=$(aws elbv2 describe-target-groups --names puff-api-tg \
  --query 'TargetGroups[0].TargetGroupArn' --output text)

echo $VPC_ID $PRIVATE_SUBNETS $TG_ARN

PRIVATE_SUBNETS must show exactly two IDs separated by a comma. If your subnets are named differently, list them with the command below and set the variable by hand.

aws ec2 describe-subnets --filters Name=vpc-id,Values=$VPC_ID \
  --query 'Subnets[].[SubnetId,AvailabilityZone,Tags[?Key==`Name`]|[0].Value]' --output table
  1. Create the Auto Scaling group and its scaling policy:
aws autoscaling create-auto-scaling-group \
  --auto-scaling-group-name puff-asg \
  --launch-template 'LaunchTemplateName=puff-api-lt,Version=$Latest' \
  --min-size 2 --max-size 4 --desired-capacity 2 \
  --vpc-zone-identifier "$PRIVATE_SUBNETS" \
  --target-group-arns $TG_ARN \
  --health-check-type ELB --health-check-grace-period 300

aws autoscaling put-scaling-policy \
  --auto-scaling-group-name puff-asg \
  --policy-name puff-cpu-50 \
  --policy-type TargetTrackingScaling \
  --target-tracking-configuration '{"PredefinedMetricSpecification":{"PredefinedMetricType":"ASGAverageCPUUtilization"},"TargetValue":50.0}'

--health-check-type ELB turns the ALB's "this server is sick" into a replacement, and the 300 second grace period gives Docker time to install and start. You'll find it all under EC2 > Auto Scaling groups > puff-asg.

  1. Wait about 3 minutes, then check the targets. Once the two new servers are healthy, retire the hand-made one:
aws elbv2 describe-target-health --target-group-arn $TG_ARN \
  --query 'TargetHealthDescriptions[].[Target.Id,TargetHealth.State]' --output table

aws elbv2 deregister-targets --target-group-arn $TG_ARN --targets Id=$API_ID
aws ec2 terminate-instances --instance-ids $API_ID
  1. Break it on purpose, terminate one ASG server and watch the group replace it.
VICTIM=$(aws autoscaling describe-auto-scaling-groups --auto-scaling-group-names puff-asg \
  --query 'AutoScalingGroups[0].Instances[0].InstanceId' --output text)
aws ec2 terminate-instances --instance-ids $VICTIM

# run this every 30 seconds or so
aws autoscaling describe-scaling-activities --auto-scaling-group-name puff-asg \
  --max-items 3 --query 'Activities[].[StartTime,StatusCode,Description]' --output table

Post a message from the frontend in the meantime: the surviving server answers it.

✅

How you know it works: within a few minutes the activity list shows "Terminating EC2 instance: i-..." followed by "Launching a new EC2 instance: i-...", and describe-target-health shows two healthy targets again, one of them new.

  1. Load test. Hit the API hard from the terminal for a few minutes:
ALB=$(aws elbv2 describe-load-balancers --names puff-alb \
  --query 'LoadBalancers[0].DNSName' --output text)
timeout 600 sh -c "seq 1 1000000 | xargs -P 40 -I{} curl -s -o /dev/null http://$ALB/api/messages" &

If hey or ab is installed (which hey ab), hey -z 10m -c 40 http://$ALB/api/messages gives nicer stats.
The browser terminal is small and may not push two servers past 50% CPU. If CPU stays low after 5 minutes, make the servers busy through Systems Manager (it stops itself after 15 minutes):

IDS=$(aws autoscaling describe-auto-scaling-groups --auto-scaling-group-names puff-asg \
  --query 'AutoScalingGroups[0].Instances[].InstanceId' --output text)

aws ssm send-command --document-name AWS-RunShellScript --instance-ids $IDS \
  --parameters '{"commands":["timeout 900 sh -c \"yes > /dev/null & yes > /dev/null & wait\""]}' \
  --query 'Command.CommandId' --output text

Then watch desired move:

aws autoscaling describe-auto-scaling-groups --auto-scaling-group-names puff-asg \
  --query 'AutoScalingGroups[0].[MinSize,DesiredCapacity,MaxSize,length(Instances)]' --output text

Desired should reach 3 or 4 after 3 to 5 minutes of high CPU, and drop back to 2 about 15 minutes after the load stops.
In CloudWatch > Alarms you'll find the TargetTracking-puff-asg-AlarmHigh-... and ...AlarmLow-... alarms the policy created for you. Don't edit them.

🧯 If it doesn't work
  • Targets stay unhealthy: open Session Manager on one instance and read sudo docker ps and sudo cat /var/log/cloud-init-output.log. Usually user data failed or the Parameter Store read was denied.
  • Instances replaced in a loop: grace period too short. Raise it with aws autoscaling update-auto-scaling-group --auto-scaling-group-name puff-asg --health-check-grace-period 600.
  • Subnet error on create: PRIVATE_SUBNETS is empty or has a tab. echo it and fix it by hand.
  • Image pull fails: the private route table must send 0.0.0.0/0 to your NAT gateway.
  • Nothing scales: check the alarm in CloudWatch. Without detailed monitoring it can take 15 minutes or more.

📦 Containers in production: ECS vs EKS vs Docker on EC2

📝

No lab for this one, ECS, EKS and ECR are blocked in the sandbox, so you learn the trade-offs here and keep running Docker on EC2 in your ASG.

You'll hear "we should move to Kubernetes" in every company you join, so you need to know when it's a good idea and when it isn't.

In production, someone has to start containers, restart them when they crash, spread them over machines and roll out new versions.
That's the job of an orchestrator, like a stage manager who knows which actor goes on which stage.

AWS gives you three realistic options:

  • Keep Docker on EC2, as you do today.
  • ECS (Elastic Container Service), AWS's own orchestrator.
  • EKS (Elastic Kubernetes Service), Kubernetes run by AWS.
  • Fargate adds "containers without servers" to ECS or EKS, you hand over an image and pay per second for machines you never see.

Don't run Kubernetes for a 3-container app.
It pays off with dozens of services and several teams, for three containers it adds a lot of moving parts to do what an ASG or a small ECS service already does.
If you can't name the Kubernetes feature you need that ECS lacks, you don't need Kubernetes yet.

At Alan we do run Kubernetes, and it pays off because of scale: many services, many engineers shipping every day, and an infra team that keeps it boring for everyone else.

🔍 Want more? Docker on EC2 vs ECS vs EKS, side by side
Docker on EC2 (your Puff today)ECS (on EC2 or Fargate)EKS (managed Kubernetes)
Who starts the containersYour user data, one container per serverAWS's own orchestratorKubernetes, with AWS running its brain
Who looks after the serversYou (ASG + AMI)You on EC2, nobody on FargateYou, or nobody with Fargate
New versions and restartsYou script themBuilt inBuilt in, very flexible
How hard to learnLowMediumHigh
Cost before running anythingNoneNone\$0.10 per hour per cluster, plus extras and people's time
Works outside AWSYesNoYes, mostly

Fargate is often the best answer for a small team. Kubernetes for three containers means a control plane, an ingress controller, access rules (RBAC, role-based access control) and upgrades every few months.

A 5 minute exercise now, the board app grows to 3 services (the API, a moderation worker, an export job) maintained by 2 developers.
Pick Docker on EC2, ECS or EKS (the table above helps), write one sentence on why, and one on what would make you switch.

🪶 Serverless: Lambda and API Gateway

Keeping a server up all month for a job that runs twice a day wastes money, like renting a car for a year to go to the airport once.

With AWS Lambda you hand AWS a function, it runs when an event happens (an S3 upload, a queue message, a web request, a timer), and you pay only for the seconds it runs, like a taxi.
There's no server to patch, and it goes from zero copies to thousands on its own.

The catch is the cold start, when no warm copy is ready Lambda sets one up first, which adds up to a few seconds.
Fine for background jobs, noticeable when a user is waiting.

API Gateway is a managed front door for web APIs (routing, login checks, rate limits) that forwards requests to Lambda.
You'll touch it in the Module 14 lab, it's not in your sandbox.

The board app's API on Lambda would cost nearly nothing at 3 a.m.
But 500 requests at once means 500 database connections on a small db.t3.micro, which falls over without a connection pooler (it shares a few connections between requests) like RDS Proxy.

🔍 Want more? Lambda's limits and billing
  • Billing is per invocation plus GB-seconds (memory multiplied by duration). A 200 ms function called a few thousand times a day costs close to nothing.
  • 15 minutes maximum per invocation.
  • 128 MB to 10,240 MB of memory, and the CPU grows with the memory you pick.
  • 6 MB maximum payload for synchronous calls.
  • 1,000 copies running at once per region by default.
  • The Init Duration field in the REPORT log line is the cold start, measured.

🧮 VM vs containers vs serverless

A VM (virtual machine) is a full server in software, like your EC2 instances.

VMs (EC2 + ASG)Containers (ECS/Fargate, EKS)Serverless (Lambda)
What you shipA disk image + a boot scriptA container imageA function
How fast it scalesMinutesSeconds to a minuteUnder a second to a few seconds
Cost when nobody uses itYou pay for running serversYou pay for running containersZero
Cost when busy all dayCheapestClose to VMsOften the most expensive
Long jobs, open connectionsYesYesNo (15 min max)

Spiky or rare work leans serverless, steady always-on work leans VMs or containers.

🔍 Want more? Daily work and lock-in
  • VMs leave you OS updates and disk images to maintain, containers leave you images and an orchestrator, and serverless leaves you almost nothing, though it's harder to test and debug on your laptop.
  • Leaving AWS later is easy from VMs, a little harder from containers on ECS, and hard from Lambda.

Now pick for Puff, VM, container or serverless for each piece, with one line on why:

  • (a) the board app's API during the course, steady traffic from 52 students for 4 hours;
  • (b) the same API used once a month by 3 people;
  • (c) a job that resizes uploaded images;
  • (d) a nightly export of all messages to S3 that takes 2 minutes;
  • (e) a WebSocket server pushing new messages live to every open browser.

🔀 Event-driven architecture: SQS and SNS

Add "send each message to a moderation service" as a direct call in the API, and posting becomes as slow and fragile as moderation.
If moderation is down, nobody can post.

Decoupling fixes that, the API drops an event somewhere, answers right away, and other parts handle it later.
Like a restaurant, the waiter pins the order on a rail and goes back to the tables, and the kitchen picks orders up at its own pace.

🅰️

SQS: a queue

SQS (Simple Queue Service) is the order rail, one worker takes each message and deletes it once done.
If workers are down, messages wait (up to 14 days).

🅱️

SNS: pub/sub

SNS (Simple Notification Service) pushes a copy of each message to every subscriber (email, Lambda, SQS queue) and stores nothing, like a newsletter.
You already use it with puff-alerts.

Together they give fan-out, one "new message" topic feeds a moderation queue and a statistics queue, each drained at its own pace.
A queue also turns a burst of 10,000 requests into a calm backlog instead of a hammered database.

🔍 Want more? Idempotency, visibility timeout and FIFO
  • SQS standard queues deliver each message at least once, so sometimes twice. Workers must be idempotent, doing the same job twice gives the same result as doing it once (setting "approved = true" is fine twice, sending a payment is not).
  • When a worker picks a message, SQS hides it for the visibility timeout. If the work takes longer than that, the message reappears and a second worker starts on it, so set the timeout above your processing time.
  • FIFO queues (first in, first out) keep messages in order and remove duplicates, at a lower throughput.
  • A message that keeps failing moves to a dead-letter queue so it doesn't block the rest.
  • An SNS subscriber that's down misses the push, unless that subscriber is a queue. Adding a new consumer means adding a subscription, with no change to the API.

🧱 Microservices vs monolith

A monolith is one app deployed in one piece, like the board app.
Microservices split it into small services with their own code, deploys and data, talking over the network.

Teams ship on their own, but every function call becomes a network call that can fail, and finding a bug means following a request across five services.

Start with a monolith with clean internal modules, and split a piece out only for a concrete reason, like a team that needs to deploy it alone.
The board app should stay a monolith forever, and you can defend that in front of a jury.

🧪 Hands-on: Puff's edge and first function

This part happens in the sandbox.
Puff gets an edge and its first function, a CloudFront distribution in front of puff-frontend-<login>, and a Lambda function puff-upload-notifier that emails you through puff-alerts when a file lands in puff-uploads-<login>.

Users load the frontend through CloudFront, which reads it from your S3 bucket, and they reach the API through puff-alb.
The ALB sends them to puff-asg, 2 to 4 servers across two private subnets in two AZs, and all of them use puff-db, which lives in one AZ.
When a server dies the group replaces it, and in a rush it adds servers up to 4, then goes back to 2.
On the side, a file landing in puff-uploads-<login> starts the Lambda function, which publishes to the SNS topic puff-alerts, and SNS sends you the email.

CloudFront in front of the frontend

  1. Create the distribution with the S3 website address as its origin. This CLI shortcut sets up a plain HTTP origin with sensible defaults:
LOGIN=yourlogin
CF=$(aws cloudfront create-distribution \
  --origin-domain-name puff-frontend-$LOGIN.s3-website-us-east-1.amazonaws.com \
  --default-root-object index.html \
  --query 'Distribution.[Id,DomainName]' --output text)

echo $CF
CF_ID=$(echo $CF | cut -d' ' -f1)
🔍 Want more? The console route

CloudFront > Distributions > Create distribution, paste the s3-website address (not the bucket the dropdown suggests), HTTP only, default root object index.html.

  1. Wait for it to deploy. It takes 5 to 15 minutes, so start the upload notifier below in the meantime:
aws cloudfront wait distribution-deployed --id $CF_ID && echo deployed
  1. Test the cache twice in a row:
CF_DOMAIN=$(aws cloudfront get-distribution --id $CF_ID --query 'Distribution.DomainName' --output text)

curl -sI https://$CF_DOMAIN/ | grep -i x-cache
curl -sI https://$CF_DOMAIN/ | grep -i x-cache
✅

How you know it works: https://dxxxxxxxxxxxxx.cloudfront.net shows your Puff page in the browser, and the second curl prints X-Cache: Hit from cloudfront.

  1. Change something visible in index.html, upload it, and see the old copy still served. Then invalidate:
aws s3 cp index.html s3://puff-frontend-$LOGIN/index.html
aws cloudfront create-invalidation --distribution-id $CF_ID --paths "/index.html" "/"
⚠️

The CloudFront page is HTTPS, your ALB is plain HTTP, and browsers refuse to let an HTTPS page call an HTTP API, that's called mixed content.
So on the CloudFront URL the message list stays empty, with a "Mixed Content" error in the browser console.
Nothing is broken on your side, HTTPS on the ALB needs a domain you own and the sandbox can't register one.

For the course, use the CloudFront URL to show caching and the S3 website URL to post messages.

🔍 Want more? How real teams fix mixed content (a good project bonus)

Add the ALB as a second CloudFront origin with an /api/* behavior (caching disabled, all methods allowed), and make the frontend call relative URLs like /api/messages. The browser then only ever talks HTTPS to CloudFront, and CloudFront talks to the ALB behind the scenes.

The upload notifier

  1. Create the uploads bucket (private, Block Public Access stays on) and collect the ARNs (Amazon Resource Names, the full IDs AWS uses for everything):
ACCOUNT=$(aws sts get-caller-identity --query Account --output text)
TOPIC_ARN=arn:aws:sns:us-east-1:$ACCOUNT:puff-alerts

aws s3 mb s3://puff-uploads-$LOGIN
aws sns get-topic-attributes --topic-arn $TOPIC_ARN --query 'Attributes.SubscriptionsConfirmed'

It should print "1" (your course 4 email). "0" means you need to confirm the subscription first.

  1. Write the function:
cat > lambda_function.py <<'EOF'
import os
import urllib.parse

import boto3

sns = boto3.client("sns")
TOPIC_ARN = os.environ["TOPIC_ARN"]


def lambda_handler(event, context):
    for record in event["Records"]:
        bucket = record["s3"]["bucket"]["name"]
        key = urllib.parse.unquote_plus(record["s3"]["object"]["key"])
        size = record["s3"]["object"].get("size", 0)
        text = f"New file in {bucket}: {key} ({size} bytes)"
        print(text)
        sns.publish(TopicArn=TOPIC_ARN, Subject="Puff: new upload", Message=text)
    return {"notified": len(event["Records"])}
EOF

python3 -m zipfile -c function.zip lambda_function.py

The SNS client sits outside the handler on purpose: it's built once per cold start and reused by every later call.

  1. Create the function with LabRole (you can't create roles in the sandbox), allow S3 to call it, and connect the bucket event:
aws lambda create-function --function-name puff-upload-notifier \
  --runtime python3.12 --handler lambda_function.lambda_handler \
  --role arn:aws:iam::$ACCOUNT:role/LabRole \
  --zip-file fileb://function.zip --timeout 10 \
  --environment "Variables={TOPIC_ARN=$TOPIC_ARN}"

aws lambda add-permission --function-name puff-upload-notifier \
  --statement-id s3-uploads --action lambda:InvokeFunction \
  --principal s3.amazonaws.com \
  --source-arn arn:aws:s3:::puff-uploads-$LOGIN --source-account $ACCOUNT

FN_ARN=$(aws lambda get-function --function-name puff-upload-notifier \
  --query 'Configuration.FunctionArn' --output text)

cat > notif.json <<EOF
{"LambdaFunctionConfigurations": [
  {"LambdaFunctionArn": "$FN_ARN", "Events": ["s3:ObjectCreated:*"]}
]}
EOF

aws s3api put-bucket-notification-configuration --bucket puff-uploads-$LOGIN \
  --notification-configuration file://notif.json

S3 checks that it's allowed to call the function when you save the notification, which is why add-permission comes first.

🔍 Want more? The console route

Lambda > Functions > Create function (Python 3.12, existing role LabRole), paste the code, set TOPIC_ARN under Configuration > Environment variables, then Add trigger > S3.

  1. Upload a file and read the logs:
echo "hello from $LOGIN" > hello.txt
aws s3 cp hello.txt s3://puff-uploads-$LOGIN/

sleep 20
aws logs tail /aws/lambda/puff-upload-notifier --since 5m
✅

How you know it works: the log shows New file in puff-uploads-<login>: hello.txt (...) followed by a REPORT line, and an email titled "Puff: new upload" arrives in your inbox within a minute.

🧯 If it doesn't work
  • CloudFront returns 403 or 404: check you used the s3-website-us-east-1 endpoint, not .s3.amazonaws.com, and that http://puff-frontend-<login>.s3-website-us-east-1.amazonaws.com works on its own.
  • put-bucket-notification-configuration fails with "Unable to validate the following destination configurations": the add-permission step is missing or has the wrong bucket ARN.
  • No log group at all: the function was never invoked. Check the bucket notification with aws s3api get-bucket-notification-configuration --bucket puff-uploads-$LOGIN.
  • Logs show AuthorizationError on Publish: wrong topic ARN (check the region and the name puff-alerts) or LabRole lacks SNS rights, tell your teacher.
  • Log is fine but no email: the subscription is pending confirmation, or the email is in spam.
