📖 Words you'll meet today
  • Cloud: computers, storage and networks you rent from someone else through the internet, by the hour or by the request.
  • AWS (Amazon Web Services): Amazon's cloud, the one we use in this course.
  • Region: a part of the world where AWS has a group of data centers, like us-east-1 in Virginia.
  • AZ (Availability Zone): one independent data center site inside a region, with its own power and network.
  • IAM (Identity and Access Management): the AWS service that decides who can do what.
  • Policy: a small JSON (a text format for structured data) document that lists what's allowed or denied.
  • Role: an identity without a password that a person or a program borrows for a while.
  • ARN (Amazon Resource Name): the full, unique name of anything on AWS, like a postal address.
  • CLI (Command Line Interface): the aws command you type in a terminal to talk to AWS.
  • S3 (Simple Storage Service): AWS's file storage. Files live in buckets.
  • Static website: a site made of files only (HTML, images), with no server code running.
  • Tenant: a customer hosted on a cloud. On Puff, the board app is your first tenant.

🧭 AWS Academy on day one

Everything you do in this course happens in AWS Academy, class "Cloud Architecting"
You never use a personal AWS account and you never pay anything, so you can break things without fear.

There are two kinds of environments, and they behave differently.

  • Course labs sit inside each module (Module 3 holds the IAM lab).
  • Each one is a ready-made scenario with a timer, in a fresh account that gets reset when you finish or time runs out.
  • The sandbox is the module "Environnement de test (sandbox)", your own open AWS account.
  • Puff lives there, and your resources stay between courses until the class closes.

The routine, every time:

  1. Open the module, click Start Lab.
  2. Wait until the dot next to AWS at the top of the page turns green (red means stopped, yellow means starting).
  3. Click AWS: the console (AWS's website for clicking around) opens in a new tab, already logged in.
  4. The page itself has a terminal with the AWS CLI and python3/boto3 already configured with your credentials.
  5. When you're done, click End Lab. The timer shows how much session time you have left.
⚠️

Stay in us-east-1 (N. Virginia).

The region selector in the top right of the console lets you pick others, and some pages will even load, but anything you create outside us-east-1 either fails or puts your account at risk.

If a resource you created "disappeared", check the region selector first.
Same rule in the sandbox: never run more than 9 EC2 instances (virtual servers) at once, or AWS Academy suspends the account.

☁️ What the cloud is, from laptop to prod

Your laptop is fine as long as you're the only one using what you build.
The day other people need it, it stops being enough.

You build the board app on your laptop: a small Python API (the part that answers requests), a PostgreSQL database and an HTML page.
You run docker compose up, it works, you show your friends on your Wi-Fi.
Now 52 students need it from anywhere, all at the same time, at 9:00 sharp.

"Prod" (production, the real thing people use) asks a lot more: a machine that never sleeps, a public address, a database with backups you've tested, security updates, enough power for the morning rush, and someone who wakes up when it breaks at 3:00.
Your laptop does none of that.

On-premises means servers you own, in a room you control.
You buy machines, wait weeks for delivery, and size everything for the busiest day of the year, so most of the year they sit idle and you've already paid for them.

In the cloud you rent instead, like a car.
Someone else owns the buildings and the hardware, you rent what you need through an API (a way for programs to send orders to another system), by the second or the hour.
A server is ready in a minute or two, and you stop paying when you give it back.

💡

The rest of this course (networks, databases, scaling, infrastructure as code) is about using that rented API well.

🏗️ So what is project Puff?

Puff is your own small cloud.

Course after course, you give it the building blocks every cloud offers: storage, compute (servers that run code), a managed database, a private network, identity and secrets, alarms, the ability to grow and shrink, and finally the whole thing written as code.

Puff needs a customer from day one, so it gets the board app, its first tenant (a customer hosted on your cloud).
People post short messages, everyone sees the list.
It's boring on purpose, we care about the cloud around it.

Puff is built on top of AWS, the way many companies run an internal platform for their own teams.
You won't rack any servers, you'll assemble AWS pieces into something that feels like a cloud to whoever runs on it.

🍕 IaaS, PaaS, SaaS

Each service you pick decides how much work you keep for yourself.
Pizza works well here: homemade, frozen or delivered.

The three models answer one question: how much of the stack do you still manage yourself?

IaaS (Infrastructure as a Service)PaaS (Platform as a Service)SaaS (Software as a Service)
You manageOperating system, runtime, app, dataYour app and dataYour data and settings
Provider managesHardware, network, virtualizationUpdates, runtimeEverything
AWS examplesEC2, EBS, VPCRDS, Elastic Beanstalk, LambdaAmazon WorkMail, Amazon Chime
Everyday examplesA VPS from any hostHeroku, VercelGmail, Slack, Notion

Puff uses all of them before the course ends.

The board app's API runs on EC2 (IaaS, you install the operating system updates), its database runs on RDS (Relational Database Service, PaaS-like: AWS installs PostgreSQL, updates it, takes backups, you only own the tables and the data).
You'll write code in a browser and chat about it on Slack (SaaS).

Moving right on the table means less work and less control.
Start as far right as you can, and only move left to IaaS when the managed option can't give you what you need.

🔍 Want more?
  • Public cloud: a provider's machines (AWS, Google Cloud, Azure) rented by anyone, each customer kept apart on shared hardware.
  • Private cloud: the same "ask by API" model on hardware owned by one organization (OpenStack, VMware). Full control, full cost.
  • Hybrid cloud: both, connected. A bank keeps its core system in its own building and runs its website in a public cloud.
  • Multi-cloud: several public providers at once. Most companies end up with one main provider plus a few others for specific needs.

📈 Elasticity, scalability, high availability

These four words come up in every job interview, and people mix them up.
For example, let’s picture a supermarket on a Saturday.

Question it answersSupermarket exampleBoard app on Puff
ScalabilityCan it handle more load if I add resources?More checkouts serve more peopleA second API server doubles capacity
ElasticityDoes it add and remove resources by itself, following demand?Extra cashiers called in when the line grows, sent home after2 servers at 8:55, 4 at 9:00, back to 2 at 9:30, without you
High availability (HA)Does it stay up when something fails, with at most a short blip?A cashier leaves, customers walk to the next checkoutA server dies, traffic moves to the other within seconds
Fault toleranceDoes it keep working with zero visible interruption?Two cashiers per checkout, nobody notices if one leavesTwo copies always serve, losing one changes nothing

Key point: high availability accepts a short interruption and recovers fast, fault tolerance hides the failure completely and costs more. Most web apps aim for high availability.

🔍 Want more?
  • You can scale vertically (a bigger machine, which has a limit and usually needs a restart) or horizontally (more machines, the cloud way).
  • Elasticity needs horizontal scaling plus automation, which is what Auto Scaling gives Puff in course 5.

⚖️ “CAP” theorem and fault tolerance

If you keep copies of your data on several machines, one day they won't be able to talk to each other.
You'll have to choose what happens then, so choose on purpose.

Take two friends with the same notebook, one in Paris, one in Lyon, calling each other after every change.
One day the phone line dies.

The CAP theorem (Consistency, Availability, Partition tolerance) says that during a network split like this one (a partition), a system with copies has to pick one of two:

  • Consistency: every read gets the latest write, or an error.
  • Availability: every request gets an answer, maybe with old data.

Networks break, so you can't skip the P.
When it happens you have one real choice: refuse to answer, or answer with what you have.

Two copies of a bank's database sit in two data centers and the link goes down. You have €100. If both sides keep accepting withdrawals, you could take €100 on each side and the bank loses money. The bank picks consistency: one side stops accepting writes until the link is back. Now take the board app in the same situation. If one side shows a message 20 seconds late, nobody cares, so it can pick availability and keep serving.

🔍 Want more?
  • You'll meet this trade-off in AWS directly. RDS Multi-AZ keeps a standby copy in a second Availability Zone and writes to both before confirming, so it picks consistency: when the main copy fails, the database is unreachable for the minute or two it takes to switch over.
  • DynamoDB (an AWS key-value database), by default, gives you "eventually consistent" reads that are cheaper and always answer, and lets you ask for strongly consistent reads when you need them.
💡

Fault tolerance starts with one rule: assume every single piece will fail, then make sure no single failure takes you down.

One server, one availability zone, one database without a standby: each one is a single point of failure.

🤝 The shared responsibility model

Most cloud disasters you read about aren't AWS's fault, and this model tells you exactly where your homework starts.

AWS looks after the cloud itself: buildings, hardware, network.
You look after what you put in it: your data, your access rules, your settings.

It's a bit like renting a flat, the landlord fixes the plumbing but the door you left open is on you.
Where the line sits depends on the service.

EC2 (IaaS)RDS (managed)S3 (managed storage)
Buildings, hardware, networkAWSAWSAWS
Operating system updatesYouAWSAWS
Database software updatesYou, if you install oneAWS (in a time slot you pick)n/a
Firewall rules (security groups)YouYoun/a
Who can access the data (IAM, bucket policies)YouYouYou
Encryption on or off, backups keptYouYouYou

Most cloud data leaks you read about are a bucket made public by mistake: AWS's storage worked fine, the settings were on the customer's side of the line.

Key point: the more managed the service, the less you own, but you always own identity, access and your data.

🗺️ Regions and Availability Zones

Where your servers live decides how fast pages load, which laws apply, and what survives a power cut.

A Region is a city-sized area with its own set of data centers: us-east-1 (N. Virginia), eu-central-1 (Frankfurt), eu-west-3 (Paris), and more than 30 others.
Regions are kept apart on purpose, so an outage in one doesn't spread.

Each Region holds several Availability Zones (AZs), named like us-east-1a, us-east-1b.
They're separate buildings in different neighborhoods of the same city, each with its own power and network, close enough to copy data in real time.
Spreading across 2 AZs is the standard way to get high availability on AWS, Puff does it from course 3.

How to pick a region:

  • Latency (the travel time of a request): closer to your users means faster pages. Paris to Frankfurt is around 10 ms, Paris to Virginia around 80 ms.
  • Law: some data has to stay in a given country or zone (GDPR, the EU's data protection law, health data, banking rules).
  • Price: the same server costs different amounts in different regions, us-east-1 is usually among the cheapest.
  • Services: new services and features often land in us-east-1 first and reach other regions months later.
🅰️

This course runs in us-east-1 because AWS Academy says so.

It's AWS's biggest region, it's cheap and it has every service, and for a student sandbox it doesn't matter where the data lives.

🅱️

A company holding Europeans' health data picks a European region like eu-central-1 (Frankfurt) or eu-west-3 (Paris).

The law wants the data in Europe, the users are in Europe, and pages load faster.

🏢

Real-world corner: at Alan, a health insurance company, we run mostly in Frankfurt because our members' health data has to stay in Europe.

Some services are global (IAM, CloudFront, Route 53, and S3 bucket names are unique worldwide), most are regional (EC2, RDS, VPC).
If you can't find something, check the region.

You can't repeat a click next week, and a real cloud is run from commands and code.

Every action on AWS is an API call. The console, the CLI and the SDKs (Software Development Kits, libraries for your own code) are three ways to send the same orders, like ordering food at the counter, by phone, or through an app.

The same question asked three ways, "who am I on AWS?":

  • Console: the account menu in the top right.
  • CLI, in the sandbox terminal: aws sts get-caller-identity
  • SDK: python3 -c "import boto3; print(boto3.client('sts').get_caller_identity()['Arn'])"

Use the console to look and the CLI to do.

🏠 How an AWS account is structured

The account is the outer wall of everything you build, and it explains a lot of the sandbox's quirks.

An AWS account is like a house: everything inside shares one bill and one front door.
Inside it:

  • The root user is the email and password that created the account.
  • It can do anything, including closing the account.
  • You protect it with MFA (multi-factor authentication, a code from your phone on top of the password), lock it away and almost never use it.
  • IAM identities (users and roles, next section) are what people and programs use day to day, each with only the permissions they need.

In the sandbox you're not root and you don't have a normal IAM user. You're signed in through a role that AWS Academy prepared, with read-only access to IAM and a list of allowed services. You'll see it in the output of aws sts get-caller-identity: the ARN says assumed-role.

🔍 Want more?
  • One account can use every region, and each regional resource lives in exactly one. Everything running in the account shows up on its bill, per hour or per request.
  • Real companies don't put everything in one account. They use many (production, testing, sandboxes, backups, security logs) grouped under AWS Organizations, so a mistake or an attack in one stays contained. Course 4 goes deeper.

🔐 IAM: who can do what

Most security problems in the cloud come down to someone or something having more rights than it needed.

IAM (Identity and Access Management) decides who can do what on AWS, like a badge system in an office building.
For every API call it checks one thing: is this identity allowed to do this action on this resource?
The default answer is no, everything is denied until a policy allows it.

What it isExample
UserA long-lived identity for one person or app, with a password and/or access keysjdupont, who logs into the console
GroupA set of users that share permissionsdevelopers, support
RoleAn identity with no password, borrowed for a while, giving temporary credentialsLabRole, which your EC2 servers will use to read a secret
PolicyA JSON document listing what's allowed or denied"read objects in bucket X"

Least privilege means giving each identity the smallest set of permissions it needs.
Start from nothing and add what's missing, never start from * (everything) and plan to tighten it later, because you won't.

Let’s read a policy together, this one is what a deploy script for Puff's frontend should need:

{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "ReadWriteFrontendFiles",
      "Effect": "Allow",
      "Action": ["s3:GetObject", "s3:PutObject"],
      "Resource": "arn:aws:s3:::puff-frontend-jdupont/*"
    },
    {
      "Sid": "ListFrontendBucket",
      "Effect": "Allow",
      "Action": "s3:ListBucket",
      "Resource": "arn:aws:s3:::puff-frontend-jdupont"
    },
    {
      "Sid": "NeverDeleteBuckets",
      "Effect": "Deny",
      "Action": "s3:DeleteBucket",
      "Resource": "*"
    }
  ]
}
  • Version is the policy language version, always 2012-10-17. Leave it as is.
  • Each Statement has an Effect (Allow or Deny), an Action (service:operation), and a Resource (an ARN, the unique name of a thing on AWS).
  • The first statement targets the files (/* at the end), the second targets the bucket itself (no /*). Listing is a bucket action, reading a file is a file action, so you need both ARNs.
  • The third statement is an explicit Deny, which always wins over any Allow from any policy. Even with an admin policy attached later, this identity can't delete a bucket.
🔍 Want more?
  • Statements can also carry a Condition (only from this IP range, only with MFA). You'll see one in course 4.
  • Companies with good habits don't give humans IAM users at all. People log in through SSO (single sign-on, one company login for every tool) and get a role for a few hours. No long-lived access keys sitting in a laptop's ~/.aws/credentials waiting to leak.
⚠️

The classic mistake is "Action": "s3:*" with "Resource": "*".

It works on the first try, that's why people ship it.
It also lets that identity read, overwrite and delete every bucket in the account.

🏛️ The Well-Architected Framework

In the final project you'll defend your Puff to a client, and this is the vocabulary for it.

AWS's Well-Architected Framework is a checklist of good habits grouped in six pillars, like the inspection list for a house.

PillarThe question it asksPuff example
Operational excellenceCan you run, change and fix it calmly?Deploy from code, have logs you can read
SecurityIs access limited and data protected?DB in a private subnet, password in Parameter Store
ReliabilityDoes it recover from failures?API spread over 2 AZs behind a load balancer
Performance efficiencyDoes it use the right resources for the load?Static files on S3 and CloudFront, not on the API
Cost optimizationAre you paying only for what you need?t3.micro instead of t3.medium when CPU sits at 5%
SustainabilityAre you wasting energy and hardware?Scale down to 2 servers at night instead of keeping 4

The pillars pull against each other (more reliability usually costs more), so be ready to explain each trade-off.

🧪 Hands-on: Exploring AWS IAM

This one is a course lab: Atelier guidé, “exploration du service Gestion des identités et des accès AWS (AWS IAM)”.
You don't build anything new, you look at users, groups and policies that already exist, put users into groups, then sign in as those users to see what they can do.

This lab gives you a full IAM playground, which the read-only sandbox can't.
Keep the policy section above open, and have a private browser window ready for signing in as another user.

While you do it, look at this:

  • The difference between an AWS managed policy (written by AWS, shared by everyone) and an inline policy (written for one group or user). Open both and compare how precise they are.
  • When a user isn't allowed to do something, the console shows an error rather than hiding the button. Read it: it names the missing action, which is how you debug permissions in real life.
  • Permissions come from the groups a user is in. Moving a user between groups changes what they can do instantly, no new password, no logout.
  • Ask yourself, for each group: is this least privilege, or did someone take a shortcut?
✅

How you know it works: signed in as a user in a read-only group, you can list resources but get an access denied error when you try to change one, and signed in as a user from an admin group, the same action succeeds.

🧯 If it doesn't work
  • You're still logged in as the lab user in the same window: use a private window for the IAM user.
  • "Access denied" for everything: you signed in with the wrong account ID in the sign-in URL, copy it again from the IAM dashboard.
  • The lab timer ran out: start the lab again, the environment comes back fresh.

🧪 Hands-on: Static website for the café

This one is a course lab too: Atelier Défi (café), création d'un site web statique pour le café (Module 4).
You build an S3 bucket that hosts the café's website from files the lab gives you, readable by anyone on the internet.

It's a challenge lab, so the instructions tell you what to achieve more than which buttons to click.
You do it in the console, then right after you do the same thing for Puff with the CLI, so pay attention to the order of the steps.
You'll probably hit a 403 error, that's normal and it's the point of the lab.

While you do it, look at this:

  • A bucket name is unique across all of AWS, so obvious names are already taken.
  • Turning on static website hosting gives you a separate endpoint URL (with s3-website in it). The normal S3 URL and the website URL don't behave the same.
  • New buckets block all public access by default. Making the site public takes two moves: loosening Block Public Access and adding a bucket policy. Ask yourself why AWS made it this annoying.
  • If the lab asks for versioning, remember it keeps every old copy, and you pay for that storage.
✅

How you know it works: the bucket's static website endpoint URL opens the café homepage in a browser, with images loading.

🧯 If it doesn't work
  • 403 Forbidden: Block Public Access is still on, or the bucket policy is missing or targets the bucket ARN without /*.
  • 404 on the website URL: static website hosting isn't enabled, or the index document name doesn't match the uploaded file.
  • Images missing: they were uploaded to a different folder than the HTML expects, check the paths in the bucket.

🧪 Hands-on: Puff's frontend bucket

This part happens in the sandbox.
You end up with a working CLI and Puff's first storage, a public S3 static website named puff-frontend-<yourlogin> serving a hello page. This bucket hosts the board app's frontend (the page people see in their browser) for the rest of the course.

  1. Open the module "Environnement de test (sandbox)", click Start Lab, wait for the green dot next to AWS, then click AWS to open the console. Check that the region in the top right says N. Virginia.
  2. In the terminal on the lab page, check the CLI and who you are:
aws --version
export AWS_DEFAULT_REGION=us-east-1

aws sts get-caller-identity

You should see JSON with your Account (12 digits) and an Arn containing assumed-role.

  1. List the regions and the AZs of us-east-1. You'll see every region exists, but you only work in one:
aws ec2 describe-regions --query 'Regions[].RegionName' --output table
aws ec2 describe-availability-zones --query 'AvailabilityZones[].[ZoneName,ZoneId]' --output table
  1. Create the bucket. Use your EPITA login in lowercase, and replace any dot with a dash (dots in bucket names cause HTTPS trouble later):
export LOGIN=jdupont
export BUCKET="puff-frontend-${LOGIN}"

aws s3api create-bucket --bucket "$BUCKET"

In us-east-1 you don't pass a location constraint. The command answers with the bucket's Location.

  1. Turn on static website hosting with index.html as the home page:
aws s3 website "s3://${BUCKET}" --index-document index.html
  1. Look at Block Public Access, then loosen it for this bucket only. The four settings come in two pairs: two about ACLs (Access Control Lists, an old permission system you won't use) and two about bucket policies. You keep the ACL blocks on and turn off the policy blocks:
aws s3api get-public-access-block --bucket "$BUCKET"
aws s3api put-public-access-block --bucket "$BUCKET" \
  --public-access-block-configuration \
  BlockPublicAcls=true,IgnorePublicAcls=true,BlockPublicPolicy=false,RestrictPublicBuckets=false
⚠️

Block Public Access is the safety net that stops a bucket from going public by accident.

Turning it off means one bad policy is all it takes to expose every file in the bucket to the whole internet, and bots scan for open buckets constantly.
Do it only on a bucket that holds public files by design (a website), never on one holding data.

In course 5, CloudFront lets you switch it back on and keep the site public.

  1. Write a bucket policy that lets anyone read objects, and nothing else:
cat > policy.json <<EOF
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "PublicReadForWebsite",
      "Effect": "Allow",
      "Principal": "*",
      "Action": "s3:GetObject",
      "Resource": "arn:aws:s3:::${BUCKET}/*"
    }
  ]
}
EOF

aws s3api put-bucket-policy --bucket "$BUCKET" --policy file://policy.json
aws s3api get-bucket-policy --bucket "$BUCKET" --query Policy --output text

Compare it with the IAM policy from the lecture: this one is attached to the bucket instead of an identity, so it needs a Principal (who the rule applies to, here *, meaning everyone).

  1. Create and upload a hello page:
cat > index.html <<EOF
<!doctype html>
<html>
  <head><meta charset="utf-8"><title>Puff</title></head>
  <body>
    <h1>Puff is coming</h1>
    <p>Hello from ${LOGIN}, served by S3 in us-east-1.</p>
  </body>
</html>
EOF

aws s3 cp index.html "s3://${BUCKET}/index.html" --content-type "text/html; charset=utf-8"
aws s3 ls "s3://${BUCKET}/"
  1. Build the website URL and test it:
echo "http://${BUCKET}.s3-website-us-east-1.amazonaws.com"
curl -i "http://${BUCKET}.s3-website-us-east-1.amazonaws.com"

Open the printed URL in your browser too.

Note it somewhere, you'll need it in course 2.

✅

How you know it works: curl -i on http://puff-frontend-<yourlogin>.s3-website-us-east-1.amazonaws.com returns HTTP/1.1 200 OK followed by your HTML, and the same URL shows "Puff is coming" in your browser.

🧯 If it doesn't work
  • BucketAlreadyExists: someone in the world has that name. Add a suffix, like puff-frontend-jdupont-1, and keep it for the whole course.
  • AccessDenied on put-bucket-policy: Block Public Access is still on for the policy settings. Run step 6 again and check with get-public-access-block.
  • 403 Forbidden in the browser: the policy is missing, or its Resource lacks /*.
  • 404 NoSuchWebsiteConfiguration: step 5 was skipped.
  • The URL doesn't load with https://: S3 website endpoints only speak HTTP. HTTPS comes with CloudFront in course 5.
  • ExpiredToken or the CLI suddenly fails: your session ended. Start the lab again and reopen the terminal, your bucket is still there.
  • You closed the terminal and $BUCKET is empty: run the two export lines from step 4 again.

🤔 Think about it

  • Imagine the board app runs on one EC2 server in us-east-1a. Is it highly available? What's the smallest change that keeps it up if that AZ goes down, and what does it cost you?
  • A startup stores French patients' appointment data. Its CTO wants us-east-1 because it's cheaper and gets features first. What do you tell them?
  • Your puff-frontend bucket ends up serving a .env file with a database password that you uploaded by mistake. Using the shared responsibility model, whose fault is it, and which two settings would have prevented it?
  • An identity has a policy allowing s3:* on *, and another policy with the NeverDeleteBuckets statement from today. Can it delete objects? Can it delete a bucket? Why?
  • When the network splits, should the board app's message list favor consistency or availability? Would your answer change if the same app were used to vote on exam grades?
💡 Hints
  • Count the single points of failure: server, AZ, database. What does a load balancer need in order to have somewhere else to send traffic?
  • Look at the four region criteria: one of them isn't about money or speed.
  • Uploading the file is on your side of the line. Think about Block Public Access and what the bucket policy's Resource covers.
  • Explicit Deny always wins, but it only covers the action it names.
  • Ask what an old or lost answer costs in each case: a late message, or a wrong vote count.
