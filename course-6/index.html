📖 Words you'll meet today
  • IaC (infrastructure as code): describing your servers, networks and databases in text files, so a tool can build them for you.
  • Template: the text file (YAML, a simple indented format) that describes what you want, like a recipe.
  • Stack: the real resources CloudFormation built from one template, managed as one block. It's the cake you get from the recipe.
  • Change set: a preview of what an update would add, modify or delete, before anything happens.
  • Drift: when the real infrastructure no longer matches the template, because someone changed it by hand.
  • Idempotent: running the same thing twice gives the same result as running it once.
  • Tenant: a customer hosted on your cloud. The board app is Puff's first one.
  • CI/CD (continuous integration / continuous delivery): automation that builds, tests and deploys every change you push.
  • Artifact: the one packaged thing you deploy, for Puff a Docker image.
  • Rollback: going back to the last version that worked.
  • FinOps: treating the cloud bill as something engineers watch, the same way they watch errors.
  • RPO / RTO: how much data you accept losing, and how long you accept being down, after a disaster.

🧱 Why infrastructure as code

Six months from now, someone has opened port 22 on puff-api-sg "for five minutes" during an incident, someone else has changed the database size from the console, and the only record of the VPC (Virtual Private Cloud, your private network) is your memory of course 3.
Nobody knows what Puff really looks like anymore.

Infrastructure as code fixes that.
You describe your cloud in text files, you keep them in Git, and a tool makes AWS match the files.

The template is like a recipe, and the running infrastructure is the cake.
If you lose the cake you bake another one, if you lose the recipe you're guessing.

Four things get better once you do this:

  • You see drift. When reality differs from the code the tool tells you, you don't wait for something to break.
  • Changes get reviewed. A firewall change becomes a pull request a classmate reads before it ships, and you keep a history of who changed what.
  • Copies are identical. A test copy and the real thing come from the same template, so "it worked in test" means something.
  • Recovery gets simple. If you lose a region you redeploy the files somewhere else, no rebuilding from screenshots at 3:00.

Write the steps, or write the end result

There are two ways to automate infrastructure, and the difference matters more than the tool you pick.

🅰️

Imperative: you write the steps

A bash script with aws ec2 create-vpc, then create-subnet, then create-nat-gateway. Run it twice and you get two VPCs.

If it crashes halfway, you work out by hand where it stopped.
It's fine for a one-off, it's painful for anything you keep.

🅱️

Declarative: you write the end result

"There is a VPC 10.0.0.0/16 with four subnets." The tool compares that with what exists and works out the steps itself.

Run it twice and the second run does nothing.
CloudFormation and Terraform both work this way.

Declarative tools are idempotent, so applying the same file again is safe, that's what lets you automate changes and review them.

📜 CloudFormation: templates, stacks, change sets

CloudFormation is AWS's own IaC service.
You give it a template written in YAML (or JSON, another text format), and it builds a stack, all the real resources that template describes, managed as one unit.

Delete the stack and everything in it goes away, in the right order, and nothing gets left behind.

A template has three sections you'll use all the time:

  • Parameters: inputs you give at deploy time, like a name prefix or a size.
  • One template can then serve several copies of Puff.
  • Resources: the only required section.
  • Each resource has a logical ID (your nickname for it inside the template), a Type (what to build) and Properties (how).
  • Outputs: values the stack shows once it's built, like a VPC ID, so people and other stacks can find them.

Here's a tiny example with comments, one bucket for Puff:

AWSTemplateFormatVersion: "2010-09-09"
Description: Tiny example, one S3 bucket

Parameters:
  Login:                          # passed at deploy time
    Type: String
    Description: Your EPITA login, used in the bucket name

Resources:
  AssetsBucket:                   # logical ID, used inside the template
    Type: AWS::S3::Bucket         # what to create
    Properties:
      BucketName: !Sub "puff-assets-${Login}"   # !Sub fills in ${Login}
      Tags:
        - Key: Project
          Value: puff

Outputs:
  BucketArn:
    Value: !GetAtt AssetsBucket.Arn   # !GetAtt reads an attribute of a resource

Two functions do most of the work.
!Ref X gives you the ID of resource X (or the value of parameter X), !GetAtt X.Attr gives you one specific attribute of it.

Every !Ref also tells CloudFormation "this depends on that", so it builds the VPC before the subnet that points at it.
When a dependency is real but invisible (a route to the internet only works once the gateway is attached), you add DependsOn by hand.

Three stack features matter in real life:

  • Change sets show you what CloudFormation would add, modify or remove, before an update.
  • It also tells you if a change means replacement, which deletes the resource and builds a new one. For a database that's a new, empty database, so read that column every time.
  • Automatic rollback puts everything back the way it was if a deploy fails halfway, so you don't end up with half a Puff.
  • Drift detection compares each resource with the template and flags anything changed by hand, like that port 22 rule.
⚠️

Once a resource belongs to a stack, change it through the stack only.

Editing it in the console creates drift, and the next stack update may quietly undo your fix or fail on it.

⚖️ CloudFormation vs Terraform

🗒️

No lab for this one, Terraform isn't part of the AWS Academy course, so we compare on paper.

Terraform (by HashiCorp) is the other big declarative tool.
You write HCL (HashiCorp Configuration Language, its own small language), run terraform plan to preview, then terraform apply to build.
The plan is the same idea as a change set.

The big difference is who runs it, AWS runs CloudFormation for you and it only speaks AWS, you run Terraform yourself and it speaks to almost every cloud and online tool.

resource "aws_vpc" "puff" {
  cidr_block = "10.0.0.0/16"
  tags       = { Name = "puff-vpc" }
}

# terraform plan  ->  + aws_vpc.puff will be created
# terraform apply ->  creates it and records the ID in the state

CloudFormation wins on zero setup and tight AWS integration, Terraform wins when your infrastructure goes beyond AWS.

Terraform keeps a state file, a JSON record that maps every resource in your code to its real ID in the cloud (aws_vpc.puff is vpc-0abc...).
On each plan it refreshes that record against reality and compares it with your code.

Teams keep state remotely (an S3 bucket with locking, for example) so two people can't apply at the same time, and they guard it carefully, because state can contain passwords in plain text.
CloudFormation's version of this mapping is the Resources tab of a stack, which AWS stores for you.

🏢

Real-world corner: at Alan, a health insurance company running on AWS, we use Terraform.

Our setup covers AWS resources, monitoring, DNS (the system that turns names into addresses), SaaS tools (software we rent online) and several AWS accounts, and we want one tool with one workflow, not a different tool per vendor.

If you only ever touch AWS, CloudFormation is a fine choice, and the habits you build today (read the preview, never click in production) carry over.

🧪 Hands-on: automating infrastructure with CloudFormation

This one is a course lab: Module 11 guided lab, automating infrastructure with AWS CloudFormation (in French, « Atelier guidé : automatisation de l'infrastructure avec AWS CloudFormation »).
You deploy a stack from a template, update it and delete it, all in AWS's pre-built lab account.

Open the lab from the course Modules list, click Start Lab and wait for the green dot.
Keep this page open next to it, the lab tells you what to click, this page tells you what to look at.

While you do it, look at this:

  • The Events tab of the stack. Resources are created in dependency order, and independent ones in parallel.
  • Nobody wrote that order by hand, it comes from the !Ref links.
  • When you update the stack, check which resources show "Modify" and which show "Replacement". Ask yourself what replacement would mean for a database.
  • The Resources tab maps logical IDs (the template's nicknames) to physical IDs (the real AWS IDs). That's how CloudFormation remembers what it built.
  • Deleting the stack removes everything, in reverse order, without you hunting through five consoles.
✅

How you know it works: the stack reaches CREATE_COMPLETE, then UPDATE_COMPLETE after your change, and the lab's check passes. You can explain in one sentence why a replacement is riskier than a modification.

🧪 Hands-on: Puff's network as code

This part happens in the sandbox.
This is the step that turns Puff into a real platform, because every tenant lives on the network.
Once it's a template, giving a new customer their own copy of Puff's network is one deploy command with a different name prefix, and you do exactly that with the prefix puff-cfn.

You write puff-network.yaml, a template that recreates your course 3 network:

  • the VPC and 4 subnets in 2 AZs (Availability Zones, separate data centers in the region),
  • the internet gateway and the NAT gateway (the one-way exit door for private servers),
  • route tables, an S3 gateway endpoint and the three chained security groups.

You deploy it as stack puff-network, update it through a change set, then delete it.

If a step fails, CloudFormation's error messages are some of the clearest in AWS, and the 🧯 toggle below covers the usual ones.

  1. Start the sandbox, open the browser terminal, and check you're in the right place:
aws sts get-caller-identity
aws configure get region   # expect us-east-1
  1. If your course 3 VPC still exists, this stack creates a second one next to it, and that's fine (names are only tags). To tell them apart, deploy with the prefix puff-cfn in step 4.
    Each VPC needs one Elastic IP (a fixed public address) for its NAT, and the default limit is 5, so release any you no longer use.
  2. Create the template. Run cat > puff-network.yaml <<'EOF', paste the whole template below, then type EOF on its own line and press Enter.
    Take a minute to read it first, every block is something you clicked in course 3.
AWSTemplateFormatVersion: "2010-09-09"
Description: Puff network, the course 3 VPC as code

Parameters:
  NamePrefix:
    Type: String
    Default: puff
    Description: Prefix for Name tags (use puff-cfn if your course 3 VPC still exists)

Resources:
  # VPC and internet access
  PuffVpc:
    Type: AWS::EC2::VPC
    Properties:
      CidrBlock: 10.0.0.0/16
      EnableDnsSupport: true
      EnableDnsHostnames: true
      Tags:
        - Key: Name
          Value: !Sub "${NamePrefix}-vpc"

  PuffIgw:
    Type: AWS::EC2::InternetGateway
    Properties:
      Tags:
        - Key: Name
          Value: !Sub "${NamePrefix}-igw"

  PuffIgwAttachment:
    Type: AWS::EC2::VPCGatewayAttachment
    Properties:
      VpcId: !Ref PuffVpc
      InternetGatewayId: !Ref PuffIgw

  # Subnets: 2 public, 2 private, spread over the first two AZs
  PublicSubnetA:
    Type: AWS::EC2::Subnet
    Properties:
      VpcId: !Ref PuffVpc
      CidrBlock: 10.0.1.0/24
      AvailabilityZone: !Select [0, !GetAZs ""]
      MapPublicIpOnLaunch: true
      Tags:
        - Key: Name
          Value: !Sub "${NamePrefix}-public-a"

  PublicSubnetB:
    Type: AWS::EC2::Subnet
    Properties:
      VpcId: !Ref PuffVpc
      CidrBlock: 10.0.2.0/24
      AvailabilityZone: !Select [1, !GetAZs ""]
      MapPublicIpOnLaunch: true
      Tags:
        - Key: Name
          Value: !Sub "${NamePrefix}-public-b"

  PrivateSubnetA:
    Type: AWS::EC2::Subnet
    Properties:
      VpcId: !Ref PuffVpc
      CidrBlock: 10.0.11.0/24
      AvailabilityZone: !Select [0, !GetAZs ""]
      Tags:
        - Key: Name
          Value: !Sub "${NamePrefix}-private-a"

  PrivateSubnetB:
    Type: AWS::EC2::Subnet
    Properties:
      VpcId: !Ref PuffVpc
      CidrBlock: 10.0.12.0/24
      AvailabilityZone: !Select [1, !GetAZs ""]
      Tags:
        - Key: Name
          Value: !Sub "${NamePrefix}-private-b"

  # Public routing: default route to the internet gateway
  PublicRouteTable:
    Type: AWS::EC2::RouteTable
    Properties:
      VpcId: !Ref PuffVpc
      Tags:
        - Key: Name
          Value: !Sub "${NamePrefix}-public-rt"

  PublicDefaultRoute:
    Type: AWS::EC2::Route
    DependsOn: PuffIgwAttachment   # the IGW must be attached before a route can use it
    Properties:
      RouteTableId: !Ref PublicRouteTable
      DestinationCidrBlock: 0.0.0.0/0
      GatewayId: !Ref PuffIgw

  PublicSubnetARouteTableAssociation:
    Type: AWS::EC2::SubnetRouteTableAssociation
    Properties:
      SubnetId: !Ref PublicSubnetA
      RouteTableId: !Ref PublicRouteTable

  PublicSubnetBRouteTableAssociation:
    Type: AWS::EC2::SubnetRouteTableAssociation
    Properties:
      SubnetId: !Ref PublicSubnetB
      RouteTableId: !Ref PublicRouteTable

  # One NAT gateway in public subnet A (cheap, but a single point of failure)
  NatEip:
    Type: AWS::EC2::EIP
    DependsOn: PuffIgwAttachment
    Properties:
      Domain: vpc
      Tags:
        - Key: Name
          Value: !Sub "${NamePrefix}-nat-eip"

  PuffNatGateway:
    Type: AWS::EC2::NatGateway
    Properties:
      AllocationId: !GetAtt NatEip.AllocationId
      SubnetId: !Ref PublicSubnetA
      Tags:
        - Key: Name
          Value: !Sub "${NamePrefix}-nat"

  # Private routing: default route to the NAT gateway
  PrivateRouteTable:
    Type: AWS::EC2::RouteTable
    Properties:
      VpcId: !Ref PuffVpc
      Tags:
        - Key: Name
          Value: !Sub "${NamePrefix}-private-rt"

  PrivateDefaultRoute:
    Type: AWS::EC2::Route
    Properties:
      RouteTableId: !Ref PrivateRouteTable
      DestinationCidrBlock: 0.0.0.0/0
      NatGatewayId: !Ref PuffNatGateway

  PrivateSubnetARouteTableAssociation:
    Type: AWS::EC2::SubnetRouteTableAssociation
    Properties:
      SubnetId: !Ref PrivateSubnetA
      RouteTableId: !Ref PrivateRouteTable

  PrivateSubnetBRouteTableAssociation:
    Type: AWS::EC2::SubnetRouteTableAssociation
    Properties:
      SubnetId: !Ref PrivateSubnetB
      RouteTableId: !Ref PrivateRouteTable

  # S3 traffic from private subnets skips the NAT (free, faster)
  S3GatewayEndpoint:
    Type: AWS::EC2::VPCEndpoint
    Properties:
      VpcId: !Ref PuffVpc
      ServiceName: !Sub "com.amazonaws.${AWS::Region}.s3"
      VpcEndpointType: Gateway
      RouteTableIds:
        - !Ref PrivateRouteTable

  # Chained security groups: internet -> ALB -> API -> DB
  AlbSecurityGroup:
    Type: AWS::EC2::SecurityGroup
    Properties:
      GroupDescription: Puff ALB, HTTP from the internet
      VpcId: !Ref PuffVpc
      SecurityGroupIngress:
        - IpProtocol: tcp
          FromPort: 80
          ToPort: 80
          CidrIp: 0.0.0.0/0
      Tags:
        - Key: Name
          Value: !Sub "${NamePrefix}-alb-sg"

  ApiSecurityGroup:
    Type: AWS::EC2::SecurityGroup
    Properties:
      GroupDescription: Puff API, port 8080 from the ALB only
      VpcId: !Ref PuffVpc
      SecurityGroupIngress:
        - IpProtocol: tcp
          FromPort: 8080
          ToPort: 8080
          SourceSecurityGroupId: !GetAtt AlbSecurityGroup.GroupId
      Tags:
        - Key: Name
          Value: !Sub "${NamePrefix}-api-sg"

  DbSecurityGroup:
    Type: AWS::EC2::SecurityGroup
    Properties:
      GroupDescription: Puff database, PostgreSQL from the API only
      VpcId: !Ref PuffVpc
      SecurityGroupIngress:
        - IpProtocol: tcp
          FromPort: 5432
          ToPort: 5432
          SourceSecurityGroupId: !GetAtt ApiSecurityGroup.GroupId
      Tags:
        - Key: Name
          Value: !Sub "${NamePrefix}-db-sg"

Outputs:
  VpcId:
    Description: Puff VPC
    Value: !Ref PuffVpc
  PublicSubnetIds:
    Description: Public subnets, for the ALB
    Value: !Join [",", [!Ref PublicSubnetA, !Ref PublicSubnetB]]
  PrivateSubnetIds:
    Description: Private subnets, for the API instances and RDS
    Value: !Join [",", [!Ref PrivateSubnetA, !Ref PrivateSubnetB]]
  AlbSecurityGroupId:
    Value: !GetAtt AlbSecurityGroup.GroupId
  ApiSecurityGroupId:
    Value: !GetAtt ApiSecurityGroup.GroupId
  DbSecurityGroupId:
    Value: !GetAtt DbSecurityGroup.GroupId
  NatGatewayId:
    Value: !Ref PuffNatGateway
  1. Validate, then deploy. This is the one command that builds a whole network.
    deploy creates a change set, executes it and waits, which takes 3 to 5 minutes (the NAT gateway is the slow one).
aws cloudformation validate-template --template-body file://puff-network.yaml
aws cloudformation deploy \
  --template-file puff-network.yaml \
  --stack-name puff-network \
  --parameter-overrides NamePrefix=puff-cfn

While it runs, open CloudFormation > Stacks > puff-network > Events and watch the order: VPC and internet gateway first, subnets and route tables in parallel, the NAT gateway last.

  1. Read the outputs. This is how the rest of your Puff (or your project group) finds the network.
aws cloudformation describe-stacks --stack-name puff-network \
  --query "Stacks[0].Outputs[].[OutputKey,OutputValue]" --output table
✅

How you know it works: aws cloudformation describe-stacks --stack-name puff-network --query "Stacks[0].StackStatus" returns "CREATE_COMPLETE", and the outputs table shows 7 rows, with two comma-separated subnet IDs in each subnet row.

  1. Optional, 3 minutes: catch drift. You add a rule behind CloudFormation's back, like the colleague from the story above, then ask it what changed.
API_SG=$(aws cloudformation describe-stacks --stack-name puff-network \
  --query "Stacks[0].Outputs[?OutputKey=='ApiSecurityGroupId'].OutputValue" --output text)

aws ec2 authorize-security-group-ingress --group-id "$API_SG" \
  --protocol tcp --port 22 --cidr 10.0.0.0/16

DRIFT_ID=$(aws cloudformation detect-stack-drift --stack-name puff-network \
  --query StackDriftDetectionId --output text)
sleep 20

aws cloudformation describe-stack-drift-detection-status \
  --stack-drift-detection-id "$DRIFT_ID" --query StackDriftStatus
aws cloudformation describe-stack-resource-drifts --stack-name puff-network \
  --stack-resource-drift-status-filters MODIFIED \
  --query "StackResourceDrifts[].LogicalResourceId"

You should see "DRIFTED" and ["ApiSecurityGroup"].

  1. Make one change through a change set. Add a cost tag to the VPC in puff-network.yaml (you'll see why in the FinOps section), so its Tags block becomes:
      Tags:
        - Key: Name
          Value: !Sub "${NamePrefix}-vpc"
        - Key: Project
          Value: puff

Then create the change set, read it, and only then execute it:

aws cloudformation create-change-set --stack-name puff-network \
  --change-set-name add-project-tag \
  --template-body file://puff-network.yaml \
  --parameters ParameterKey=NamePrefix,UsePreviousValue=true
aws cloudformation wait change-set-create-complete \
  --stack-name puff-network --change-set-name add-project-tag
aws cloudformation describe-change-set --stack-name puff-network \
  --change-set-name add-project-tag \
  --query "Changes[].ResourceChange.[Action,LogicalResourceId,Replacement]" --output table
aws cloudformation execute-change-set --stack-name puff-network \
  --change-set-name add-project-tag
aws cloudformation wait stack-update-complete --stack-name puff-network

The change set should list one line: Modify | PuffVpc | False. A tag is an in-place change.
Change CidrBlock instead and you'd see True, which means a brand-new VPC, so read this table before executing, every time.

  1. Delete the stack. The NAT gateway bills by the hour even with zero traffic, so don't leave it running.
aws cloudformation delete-stack --stack-name puff-network
aws cloudformation wait stack-delete-complete --stack-name puff-network
aws ec2 describe-nat-gateways --filter Name=tag:Name,Values=puff-cfn-nat \
  --query "NatGateways[].State"
✅

How you know it works: wait stack-delete-complete returns without error, and the last command prints ["deleted"] (or [] once AWS forgets it).

Stretch: add the ALB (Application Load Balancer, it spreads requests across your servers) and its target group to the template.
Append these resources under Resources, add the two outputs, and update the stack through a change set as in step 7 (redeploy first if you deleted it).

  PuffAlb:
    Type: AWS::ElasticLoadBalancingV2::LoadBalancer
    DependsOn: PuffIgwAttachment
    Properties:
      Type: application
      Scheme: internet-facing
      Subnets: [!Ref PublicSubnetA, !Ref PublicSubnetB]
      SecurityGroups: [!GetAtt AlbSecurityGroup.GroupId]
      Tags:
        - Key: Name
          Value: !Sub "${NamePrefix}-alb"

  PuffTargetGroup:
    Type: AWS::ElasticLoadBalancingV2::TargetGroup
    Properties:
      VpcId: !Ref PuffVpc
      Protocol: HTTP
      Port: 8080
      TargetType: instance
      HealthCheckPath: /health
      Matcher:
        HttpCode: "200"

  PuffHttpListener:
    Type: AWS::ElasticLoadBalancingV2::Listener
    Properties:
      LoadBalancerArn: !Ref PuffAlb
      Protocol: HTTP
      Port: 80
      DefaultActions:
        - Type: forward
          TargetGroupArn: !Ref PuffTargetGroup
  AlbDnsName:
    Value: !GetAtt PuffAlb.DNSName
  TargetGroupArn:
    Value: !Ref PuffTargetGroup

curl -i http://<AlbDnsName>/health should answer 503 Service Temporarily Unavailable, the ALB works but it has no healthy targets yet.
Point an Auto Scaling group at TargetGroupArn and it turns into a 200.

🧯 If it doesn't work
  • Template format error or YAML not well-formed: the paste lost indentation. Check with head -20 puff-network.yaml, every level is two spaces, no tabs.
  • Stack in ROLLBACK_COMPLETE: a creation failed and was rolled back. Find the first CREATE_FAILED line in the Events tab, fix it, then aws cloudformation delete-stack --stack-name puff-network before deploying again (a stack in that state can't be updated).
  • The maximum number of addresses has been reached: you hit the Elastic IP limit. Release unused ones in EC2 > Elastic IPs.
  • No changes to deploy: your file is identical to what's deployed. Did you save the edit?
  • DELETE_FAILED on a subnet or security group: something outside the stack (an instance, an ALB from another exercise) still uses it. Delete that first, then retry delete-stack.
  • AccessDenied on ec2:CreateVpc or CreateNatGateway: tell me straight away, it's a sandbox restriction, not your template.

🚚 CI/CD: from a commit to production

🗒️

No lab for this one, CodePipeline and CodeBuild aren't available in the sandbox, so you read a pipeline instead of running one.

Deploys are risky, and a deploy from someone's laptop on a Friday evening is worse.
CI/CD takes the manual work out of it.

Continuous integration means every change pushed to Git is built and tested automatically, like a robot that checks every homework before it's handed in.
Continuous delivery means every change that passes can go live through the same automated path.

The pipeline is a few stages in a row, and each one only runs if the previous one passed:

  • Build turns source code into an artifact: one packaged, versioned thing you deploy.
  • For the board app, a Docker image tagged with the Git commit ID (its SHA, a unique fingerprint).
  • Test runs that exact artifact: unit tests, then the container against a real PostgreSQL database.
  • Deploy pushes the same artifact to a test copy (staging) first, then to production, often with a human approval in between.

Build once, promote the same image everywhere.
If you rebuild for production, production runs something you never tested.

🔍 Want more? A real pipeline for the board app

Here's what a GitHub Actions pipeline for the board app could look like. You can't run it in the course (no ECR, AWS's private image registry, and no GitHub access to your sandbox), so read it as a design.
123456789012 is AWS's placeholder account number for docs, and puff-app.yaml is the app template you'd get by growing today's stretch.

name: puff-api
on:
  push:

🎭 Deployment strategies

Once the new image exists, you need to swap it in without anyone noticing.
There are three usual ways to do it.

  • Rolling replaces your servers a few at a time.
  • Blue/green builds a full second set of servers next to the live one, then moves all traffic at once.
  • Canary sends a small share of traffic to the new version first, and you watch what happens.
RollingBlue/greenCanary
HowReplace servers a few at a time (an instance refresh of the ASG, the Auto Scaling group)Build a full second fleet (green) next to the live one (blue), then switch all traffic at onceSend a small share of traffic (say 10%) to the new version, watch, then go to 100%
On Puffpuff-asg replaces 1 instance at a time behind puff-albTwo target groups, puff-tg-blue and puff-tg-green, the ALB listener points at one, deploying means repointing the listenerSame two target groups, the listener splits traffic 90/10, then 0/100
Going backAnother rolling deploy of the old version (slow)Point the listener back at blue (seconds)Set the new version's share back to 0 (seconds)
Extra cost during the deployNoneDouble the servers for a whileA little
Watch outOld and new versions run at the same time, so the database must work with bothBlue and green share one database, so both must accept its structureYou need good alarms, or you won't see the 10% failing

On Puff, users reach puff-alb, and its listener is the rule that decides where each request goes.
The listener points at a target group, which is a list of servers. Blue is the current Auto Scaling group, green is the new one, and both use the same database.

With blue/green, green gets built while blue still serves everyone, then the listener flips all traffic to green.
If something breaks you flip it back to blue, in seconds.

With canary, the same listener splits traffic by weight, 90% to blue and 10% to green, and you watch the alarms.
If they fire you set green back to 0, in seconds. If they stay quiet you move all traffic to green.

Blue/green and canary give you an instant way back by keeping the old version alive.
The database is what makes every strategy hard, because there's only one.

💸 FinOps: knowing what you pay for

🗒️

No lab for this one, Cost Explorer, billing and budgets are blocked in the sandbox, so we use the public AWS Pricing Calculator.

In the cloud, whoever picks the server size is spending money, often without seeing the bill.
FinOps means engineers look at cost the way they look at errors and speed.

When your group defends its Puff, "what does it cost?" will be one of my first questions.

The usual cost surprises

  • NAT gateway data. You pay per hour and per GB through it, that's why your template sends S3 traffic through the free gateway endpoint.
  • Idle resources. A NAT gateway, a load balancer or a database costs the same with zero visitors, so a forgotten test stack still bills all weekend.
  • Oversized servers, like a big m5.2xlarge picked "to be safe" that sits at 4% CPU for a year.
  • Data going out. Traffic to the internet costs per GB past a free allowance, and so does traffic between AZs and regions, traffic coming in is free.
  • Forgotten leftovers. Old disk snapshots, unattached disks and machine images pile up.
  • Public IPv4 addresses. Every one (your NAT's Elastic IP, the ALB's addresses) is billed per hour.

For a real Puff, you'd cover the two always-on API servers and the database with commitments and let Spot absorb the peaks.

🔍 Want more? Tagging and rightsizing

You can't cut what you can't see.
A tag like Project=puff (the one you added in step 7), Environment=staging or Owner=team-name lets the billing tools split the bill.

People miss two details, a tag must be switched on as a cost allocation tag in the billing console before it appears in reports, and it only counts from that day.
Tags added by hand get forgotten, so put them in the template (CloudFormation stack tags spread to the resources) or in Terraform's defaults.

Rightsizing means matching size to real use. Look at two weeks of CloudWatch CPU (memory needs the CloudWatch agent): if the peak stays well under 40%, try one size down.
Burstable t3 servers are a good default for mostly idle services like the board app, as long as they don't run out of CPU credits.

Separate AWS accounts per team or environment are the most reliable cost split, because you don't depend on anyone adding a tag.

🛟 Disaster recovery in one table

DR (disaster recovery) is your plan for the day a whole region goes down, and two numbers define it:

  • RPO (recovery point objective) is how much data you accept losing, counted in time.
  • RTO (recovery time objective) is how long you accept being down.

Smaller numbers always cost more.

StrategyWhat runs in the backup regionRPORTOCost
Backup and restoreNothing, only backupsHoursHours to a day\$
Pilot lightData copied, the database running, app servers offMinutesTens of minutes to hours\$\$
Warm standbyA small but complete copy, scaled up when neededSeconds to minutesMinutes\$\$\$
Multi-site (active/active)The full stack serving traffic in both placesNear zeroNear zero\$\$\$\$

Today's work helps here.
With puff-network.yaml and templates like it, "restore" means deploying them in another region and loading the latest backup, you don't rebuild by hand under stress.

Many companies also copy backups to a separate AWS account, so one bad mistake (or one stolen credential) can't delete everything.
