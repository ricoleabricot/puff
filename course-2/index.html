📖 Words you'll meet today
  • EC2 (Elastic Compute Cloud): the AWS service that rents you virtual machines.
  • Instance: one virtual machine running on EC2.
  • AMI (Amazon Machine Image): the template an instance boots from, an operating system plus whatever was installed on it.
  • AZ (Availability Zone): one group of data centers inside a region. us-east-1 has several, far enough apart that a fire in one doesn't reach the others.
  • EBS (Elastic Block Store): a disk that lives on the network and plugs into one instance.
  • User data: a script an instance runs by itself, once, on its first boot.
  • Security group: a firewall around a resource, a bouncer with a guest list.
  • RDS (Relational Database Service): a SQL database that AWS runs and looks after for you.
  • Managed service: AWS does the boring operations (backups, patches, repairs) and you use the result.
  • DynamoDB: AWS's key-value database with no server for you to size or patch.
  • Container: your app plus everything it needs, packed into one image that runs the same everywhere.
  • Tenant: a customer hosted on your cloud. Puff's first tenant is the board app.

🖥️ EC2: a computer you rent by the second

Your code needs a computer to run on.
Buying one means waiting weeks and paying for it even while it sleeps, so instead you rent one from AWS in about a minute and pay by the second.

That rented computer is an EC2 instance, a virtual machine living in one Availability Zone.
It's like a hotel room, you pick the size, you check in, you check out, and someone else fixes the plumbing.

Launching one means four choices:

  • what it boots (the AMI),
  • how big it is (the instance type),
  • what disk it gets,
  • what it does on first boot (user data).

The network part waits for next course.

An AMI is what the instance boots from, like a fresh laptop with the operating system already installed.
We use Amazon Linux 2023, its package manager is dnf.

The instance type is the room size. A t3.micro has 2 vCPUs (virtual processors) and 1 GiB of memory, plenty for the board app.
Families exist because apps need different things:

FamilyBuilt forPick it whenExample
T (t3, t4g)Short bursts of CPUThe CPU is mostly idle with short spikesA small API, a dev box, the board app
M (m7i, m7g)A bit of everythingYou don't know yet, and the load is steadyA web app with real traffic
C (c7i, c7g)Raw CPUThe processor is what slows you downVideo encoding, batch jobs, busy APIs
R (r7i, r7g)Lots of memoryYour data must fit in RAMCaches you run yourself, in-memory analytics
I (i4i)Very fast local diskYou read and write the disk nonstopDatabases or search engines you run yourself
G, P (g5, p5)GPUsYou train or serve machine learning modelsInference servers

Start small in T or M, measure for a week, then resize.
Resizing is stop, change type, start, so a wrong guess costs you five minutes.

🔍 Want more? Reading an instance type name, baking an AMI
  • You can bake your own AMI from a configured instance, boots get faster but you rebuild the image every time you patch something.
  • In m7g.large, m is the family, 7 the generation, g means Graviton (AWS's own ARM processor), and large is the size.
  • Each size step roughly doubles the resources and the price: large, xlarge, 2xlarge, and so on.
⚠️

T instances earn CPU credits while idle and spend them when busy, like a phone plan with rollover data.

A t3 running at 100% CPU for hours either gets slowed down (throttled) or, in the default "unlimited" mode, bills you for extra credits.
If your CPU graph is a flat line at the top, you picked the wrong family.

💾 Where your data lives on a server

Servers die, and when yours does, the question is which files die with it.
AWS gives you four places to keep data, and they don't behave the same when that happens.
EBS is like a USB drive plugged in through the network, EFS is the Elastic File System, and S3 is the storage you met in course 1.

EBSInstance storeEFSS3
What it isA disk over the networkA physical disk in the host machineA shared folder (NFS)Files you fetch over HTTP
Plugged intoOne instance, one AZThat instance onlyMany instances, many AZsNothing, you call an API
Survives a stopYesNo, wipedYesYes
Survives terminateOnly if "delete on termination" is offNoYesYes

Treat the instance and its disks as disposable.
Anything you can't lose goes to RDS, S3 or EFS, because in next courses, Puff will kill and replace your instances automatically.

🔍 Want more? Disk details
  • EBS snapshots are backups of a disk that only store what changed since the last one.
  • Your sandbox allows gp2 disks up to 35 GB, and the board app needs about 2.

🚀 User data and getting into the box

User data is a script the instance runs once, as root (the admin user), on its first boot.
A tool called cloud-init reads it and runs it.

It's the cheapest automation there is, the instance sets itself up from a stock image and you never log in to install anything.

The script's output lands in /var/log/cloud-init-output.log.
That's the first file to read when something didn't start.

Sometimes you still need a shell on the machine, and there are two ways in.

🅰️

SSH with a key pair

SSH (Secure Shell) is the classic way to log into a remote machine. AWS stores the public key and you keep the private one (vockey in the sandbox).

You need port 22 open in the security group and a public IP.
Keys get copied, shared and forgotten, and an open port 22 gets scanned by bots within minutes.

🅱️

Session Manager

An agent on the instance calls out to AWS, and you open a shell from the console or the CLI.

No open port, no key, and IAM (AWS's badges and keys system) decides who gets in and logs every session.

💶 Paying for EC2

The same machine can cost very different prices, depending on what you promise AWS.
It's like a taxi meter (On-Demand), a gym subscription (Savings Plans) or a standby plane ticket (Spot).

ModelHow it worksDiscount vs On-DemandUse it for
On-DemandPay per second, stop anytimeNoneNew workloads, spiky or short-lived things, the sandbox
Savings PlansPromise to spend a fixed \$/hour for 1 or 3 yearsUp to about 72%The steady base you'll run all year anyway
Reserved InstancesPromise to run one specific instance type for 1 or 3 yearsUp to about 72%Same idea, older and less flexible (still common for RDS)
SpotUse AWS's spare machines, AWS can take them backUp to about 90%Work that can be interrupted: test runners, batch jobs, rendering

The discount grows with what you give AWS, time for Savings Plans, the right to interrupt you for Spot.
Spot is a bad idea for anything that can't stop at two minutes' notice, like your only API server.

🔍 Want more? Spot in practice

If the work can save its progress and retry (a batch job, a test run), that's 70 to 90% off.
If it holds data, losing the instance means your app is down.

A sensible mix is a Savings Plan for the base, On-Demand for peaks, Spot for work that doesn't mind dying.

💡

Commitments lock you in for years, so make them your last step.
First pick the right sizes and turn off what sits idle, then commit to what's left.

🐳 Containers on a plain VM

You already know Docker, so the question is where the containers run.

AWS has two container platforms:

  • ECS (Elastic Container Service) is its own, often used with Fargate so there are no servers for you to manage.
  • EKS (Elastic Kubernetes Service) is managed Kubernetes.

Both are orchestrators, they decide which container runs on which machine.
Neither is available in your sandbox, so we run Docker straight on EC2, install it in user data, build the image, docker run it with a restart policy.

For a small app that's a valid real-world setup, one image you can rebuild, the same everywhere, nothing new to learn.
You give up what the orchestrator does, rolling out new versions without downtime, moving containers off a dead machine, packing many services onto few machines.

With one service and a handful of instances, Kubernetes is overhead.
Use it when you have many services and a team to run it.

🏢

Real-world corner: at Alan, a health insurance company, our apps run in containers on Kubernetes clusters, described in Terraform (a tool that writes infrastructure as code).

That makes sense for many services and many engineers. It would be absurd for one Flask API.

🗄️ RDS: what "managed" means

The database is the one piece of your app you can't rebuild from a script, lose it and the messages are gone.

RDS runs a relational engine (PostgreSQL, MySQL, MariaDB, Oracle, SQL Server, Aurora) on machines AWS operates, like renting a flat with a caretaker instead of owning a house.
You get an address like puff-db.abc123xyz.us-east-1.rds.amazonaws.com (the endpoint) and no shell on the server.

AWS handles:

  • Backups, a daily snapshot plus a log of every change, kept 1 to 35 days, so you can rewind to any second inside that window (point-in-time recovery).
  • Patching, small version updates and OS patches happen during a maintenance window you choose.
  • Failover, with Multi-AZ a twin database in another AZ receives every write.
  • If the main one dies, RDS points the endpoint name to the twin, usually in a minute or two, and your app reconnects to the same address.
  • Your sandbox doesn't allow Multi-AZ, but real databases should have it.
  • Storage and monitoring, the disk grows without downtime, and metrics land in CloudWatch, AWS's monitoring service.

The table design, slow queries, indexes, how many connections you open, passwords, sizing and the bill stay your job.

RDS PostgreSQLPostgreSQL on EC2
SetupA form or one CLI commandYou install, configure and lock it down
Backups and restoreBuilt in, rewind to any secondYou script pg_dump or log archiving and test restores
Surviving a crashTick the Multi-AZ boxYou build replication and failover
ControlNo superuser, limited extensionsFull root, any extension, any version
CostHigher per hourLower per hour, higher in your time

The hours of human work you save on backups and failover are worth far more than the price difference.
Run it yourself only when you need something RDS can't do.

🧮 DynamoDB or RDS?

Picking the wrong kind of database hurts for years, because data is hard to move.

DynamoDB is a serverless key-value and document database, no instance to size, millisecond reads at any scale, and you pay per request.
It's like a giant coat check, hand over your ticket and you get your coat back instantly, but you can't ask for every red coat.
So you design the table around the questions you'll ask it, up front, and there are no joins.

RDS (relational)DynamoDB
How data looksTables that reference each otherItems fetched by their key
Questions you can askAny SQL, even ones you invent laterOnly what your keys and indexes allow
GrowingBigger instance, read-only copiesAutomatic, nearly unlimited
Work for youInstance size, connections, maintenanceAlmost none
Good forBusiness data with relations, reporting, future questionsSessions, shopping carts, device state, lookups by ID

Pick by how you'll read the data.
Relations and questions nobody has written yet go relational, huge volumes of lookups by key go to DynamoDB.

An insurer's members, contracts and claims reference each other and get queried in ways nobody predicted on day one, that's relational.
A "last seen" time per mobile phone, read and written millions of times a day by device ID, is a DynamoDB table.

The board app uses PostgreSQL, it's the safe default, and "list the 20 latest messages" is one line of SQL.

🧰 Purpose-built databases

AWS sells one database per shape of data.
You won't use most of them this week, but you should recognize them on an architecture diagram.

Start with PostgreSQL and add a purpose-built engine when you can name the query it makes fast.

🏗️ The 3-tier app, from your laptop to the cloud

Most web apps have three tiers, like a restaurant:

  • the dining room is the presentation tier (the browser),
  • the kitchen is the logic tier (the API),
  • the fridge is the data tier (the database).

Each one only talks to its neighbor, so you can grow, protect or replace them separately.

On your laptop, it fits in a compose.yaml next to the code below:

services:
  db:
    image: postgres:16
    environment:
      POSTGRES_DB: puff
      POSTGRES_USER: puff
      POSTGRES_PASSWORD: localdev
    healthcheck:
      test: ["CMD", "pg_isready", "-U", "puff"]
      interval: 2s
      retries: 15
  api:
    build: .
    ports:
      - "8080:8080"
    environment:
      DB_HOST: db
      DB_NAME: puff
      DB_USER: puff
      DB_PASSWORD: localdev
    depends_on:
      db:
        condition: service_healthy

Moving to the cloud means swapping each line for an AWS piece.
Today is the most direct swap, and Puff improves it piece by piece over the next courses:

On your laptopToday on AWSWhere it ends up
db container and its volumeRDS puff-db in the default VPCRDS in private subnets (course 3)
api built from the DockerfileDocker on EC2 puff-api, built by user dataAuto Scaling group behind a load balancer (courses 3 and 5)
Opening index.html locallyS3 static websiteBehind CloudFront, AWS's content delivery network (course 5)
ports: 8080:8080Port 8080 open to the internetOnly the load balancer is public (course 3)
Password in environment:Password in a docker run -eSSM Parameter Store (course 4)
docker compose upYou, typing CLI commandsCloudFormation (course 6)

The default VPC (Virtual Private Cloud) is the ready-made network every AWS account starts with.

The browser loads index.html from your S3 bucket, then calls puff-api on EC2 by its public IP, on port 8080.
puff-api reads and writes messages in puff-db on port 5432, and both sit in the default VPC.
Anyone can reach the bucket and port 8080, only puff-api can reach puff-db.

🧪 Hands-on: create an RDS database

This one is a course lab too, the Module 6 guided lab, creating an Amazon RDS database (FR: « Atelier guidé : création d'une base de données Amazon RDS »).
You build an RDS instance inside a lab VPC, reached by a web server through security groups.

The VPC and web server are already built, you add the database and connect the two.
Creation takes several minutes, so read ahead meanwhile.

While you do it, look at this:

  • The database's security group lets in traffic from the web server's security group, not from a range of IP addresses. That's how you'll wire puff-db-sg later today.
  • The DB subnet group covers two AZs. RDS insists on it even for a single-AZ database, so a twin or a restore has somewhere to go.
  • The app connects to an endpoint name, never to an IP. Why does that matter when the database fails over to its twin?
✅

How you know it works: the lab's web app reads and writes rows in your RDS database.

🧪 Hands-on: migrate the café database to RDS

This one is the optional course lab, the Module 6 café challenge lab, migrating a database to Amazon RDS (FR: « Atelier Défi (café) : migration d'une base de données vers Amazon RDS »).
You move the café's local database onto RDS and point the app at it.

It's the classic first migration, export, import, change the connection setting.
Do it if you finish the board app's deploy early, or at home.

While you do it, look at this:

  • Export then import is a copy at one moment in time. Anything written in between is lost unless you stop the app, so a real migration plans a downtime window or copies changes live (replication).
  • The app change is one setting. Apps that read their database address from config instead of code are cheap to move.
✅

How you know it works: the café site shows the same orders as before, and they're stored in RDS.

🧪 Hands-on: Puff gets compute and a database

This part happens in the sandbox.
You do the naive deploy, Puff gets compute and a database, and the board app goes live.
The frontend on your course 1 S3 bucket calls the API on EC2 puff-api, which stores messages in RDS puff-db.

Something will probably fail along the way, and that's fine.
Every error teaches you how a piece of AWS works, and the 🧯 toggle below lists the usual ones.

1. Start the sandbox and set your variables.
Open the "Environnement de test (sandbox)" module, click Start Lab, wait for the green dot, and use the browser terminal on the page.
Replace yourlogin with the login you used for your bucket in course 1.

export LOGIN=yourlogin
export AWS_DEFAULT_REGION=us-east-1
export DB_PASSWORD=$(python3 -c "import secrets; print(secrets.token_hex(12))")

2. Create the board app's code.
This page is the only place the code lives.
Paste each block into the terminal and it creates the file in ~/puff. Read app.py before you paste it, it's short.

cat > app.py <<'EOF'
import os

import psycopg
from flask import Flask, jsonify, request
from psycopg.rows import dict_row

app = Flask(__name__)


def db():
    return psycopg.connect(
        host=os.environ["DB_HOST"],
        dbname=os.environ.get("DB_NAME", "puff"),
        user=os.environ.get("DB_USER", "puff"),
        password=os.environ["DB_PASSWORD"],
        connect_timeout=5,
        row_factory=dict_row,
    )


with db() as conn:  # runs once at startup: create the table if missing
    conn.execute(
        "CREATE TABLE IF NOT EXISTS messages ("
        " id SERIAL PRIMARY KEY, author TEXT NOT NULL, text TEXT NOT NULL,"
        " created_at TIMESTAMPTZ NOT NULL DEFAULT now())"
    )


@app.after_request
def cors(resp):  # lets the S3 website (another origin) call this API
    resp.headers["Access-Control-Allow-Origin"] = "*"
    resp.headers["Access-Control-Allow-Headers"] = "Content-Type"
    resp.headers["Access-Control-Allow-Methods"] = "GET, POST, OPTIONS"
    return resp


@app.get("/health")
def health():
    return {"status": "ok"}


@app.get("/api/messages")
def list_messages():
    with db() as conn:
        rows = conn.execute(
            "SELECT id, author, text, created_at FROM messages"
            " ORDER BY id DESC LIMIT 20"
        ).fetchall()
    return jsonify(rows)


@app.post("/api/messages")
def post_message():
    data = request.get_json(silent=True) or {}
    author = str(data.get("author", "")).strip()[:40]
    text = str(data.get("text", "")).strip()[:280]
    if not author or not text:
        return {"error": "author and text are required"}, 400
    with db() as conn:
        row = conn.execute(
            "INSERT INTO messages (author, text) VALUES (%s, %s)"
            " RETURNING id, author, text, created_at",
            (author, text),
        ).fetchone()
    return jsonify(row), 201
EOF
cat > requirements.txt <<'EOF'
flask>=3.0,<4
psycopg[binary]>=3.2,<4
gunicorn>=22,<24
EOF
cat > Dockerfile <<'EOF'
FROM python:3.12-slim
WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY app.py .
EXPOSE 8080
CMD ["gunicorn", "--bind", "0.0.0.0:8080", "--workers", "2", "--preload", "--access-logfile", "-", "app:app"]
EOF
🔍 Want more? Why the code looks like this
  • Each request opens a short-lived database connection, which is fine at this scale.
  • The %s placeholders let psycopg escape the values, so nobody can slip SQL commands in through the form (SQL injection).
  • --preload loads the app once before gunicorn starts two workers, so CREATE TABLE runs once.
  • The CORS (Cross-Origin Resource Sharing) header exists because the page comes from your S3 website, a different origin, and browsers block the call unless the API says it's allowed.

And the frontend, with the API address in one constant at the top of the script:

cat > index.html <<'EOF'

    async function load() {

3. Create the security groups.
One for the API, one for the database.
The database's group only lets in instances that have the API's group.

VPC_ID=$(aws ec2 describe-vpcs --filters Name=isDefault,Values=true \
  --query 'Vpcs[0].VpcId' --output text)

API_SG=$(aws ec2 create-security-group --group-name puff-api-sg \
  --description "Puff API" --vpc-id "$VPC_ID" --query GroupId --output text)

DB_SG=$(aws ec2 create-security-group --group-name puff-db-sg \
  --description "Puff database" --vpc-id "$VPC_ID" --query GroupId --output text)

# Sin: API open to the whole internet. Course 3 puts it behind a load balancer.
aws ec2 authorize-security-group-ingress --group-id "$API_SG" \
  --protocol tcp --port 8080 --cidr 0.0.0.0/0

# Sin: SSH open to the whole internet, for debugging. Course 4 replaces it with Session Manager.
aws ec2 authorize-security-group-ingress --group-id "$API_SG" \
  --protocol tcp --port 22 --cidr 0.0.0.0/0

# Good: PostgreSQL only from the API's security group.
aws ec2 authorize-security-group-ingress --group-id "$DB_SG" \
  --protocol tcp --port 5432 --source-group "$API_SG"

echo "VPC=$VPC_ID API_SG=$API_SG DB_SG=$DB_SG"

0.0.0.0/0 means "every address on the internet". Each line marked "Sin" is a shortcut we'll pay back in a later course.

4. Create the database.
In the console, this is RDS > Databases > Create database with:

  • Standard create, PostgreSQL, Free tier or Dev/Test template
  • identifier puff-db,
  • master username puff,
  • your password, db.t3.micro,
  • 20 GB gp2, single-AZ, default VPC, Public access No,
  • security group puff-db-sg (remove default),
  • initial database name puff (under Additional configuration, easy to miss),
  • Enhanced monitoring unchecked.

The CLI does the same in one command:

aws rds create-db-instance \
  --db-instance-identifier puff-db \
  --engine postgres \
  --db-instance-class db.t3.micro \
  --allocated-storage 20 \
  --storage-type gp2 \
  --db-name puff \
  --master-username puff \
  --master-user-password "$DB_PASSWORD" \
  --vpc-security-group-ids "$DB_SG" \
  --no-multi-az \
  --no-publicly-accessible \
  --backup-retention-period 1 \
  --monitoring-interval 0 \
  --no-enable-performance-insights

aws rds wait db-instance-available --db-instance-identifier puff-db   # 5 to 10 minutes

export DB_HOST=$(aws rds describe-db-instances --db-instance-identifier puff-db \
  --query 'DBInstances[0].Endpoint.Address' --output text)
echo "$DB_HOST"

5. Build the user data script.
This generates user-data.sh from the files you created, it installs Docker, writes the three files, builds the image and runs the container.
Your shell fills in $DB_HOST and $DB_PASSWORD right now, so the password ends up in plain text inside the script.

cat > user-data.sh <<EOF
#!/bin/bash
# Puff API bootstrap: runs once, as root, on first boot
set -euxo pipefail
dnf install -y docker
systemctl enable --now docker
mkdir -p /opt/puff && cd /opt/puff
cat > app.py <<'FILE'
$(cat app.py)
FILE
cat > requirements.txt <<'FILE'
$(cat requirements.txt)
FILE
cat > Dockerfile <<'FILE'
$(cat Dockerfile)
FILE
docker build -t puff-api .
docker run -d --name puff-api --restart unless-stopped -p 8080:8080 \\
  -e DB_HOST=$DB_HOST -e DB_NAME=puff -e DB_USER=puff \\
  -e DB_PASSWORD=$DB_PASSWORD \\
  puff-api
EOF
cat user-data.sh   # read it: this is exactly what the instance will run

6. Launch puff-api.
Amazon Linux 2023, t3.micro, LabInstanceProfile, default VPC (whose subnets hand out a public IP automatically).
In the console that's EC2 > Instances > Launch instance, with the contents of user-data.sh pasted in Advanced details > User data. From the terminal:

aws ec2 run-instances \
  --image-id resolve:ssm:/aws/service/ami-amazon-linux-latest/al2023-ami-kernel-default-x86_64 \
  --instance-type t3.micro \
  --key-name vockey \
  --iam-instance-profile Name=LabInstanceProfile \
  --security-group-ids "$API_SG" \
  --user-data file://user-data.sh \
  --tag-specifications 'ResourceType=instance,Tags=[{Key=Name,Value=puff-api}]' \
  --query 'Instances[0].InstanceId' --output text

aws ec2 wait instance-running --filters Name=tag:Name,Values=puff-api

export API_IP=$(aws ec2 describe-instances \
  --filters Name=tag:Name,Values=puff-api Name=instance-state-name,Values=running \
  --query 'Reservations[0].Instances[0].PublicIpAddress' --output text)
echo "$API_IP"

Give it two or three minutes after "running", Docker installs, the base image downloads from Docker Hub, pip installs the dependencies.

curl -s "http://$API_IP:8080/health"

7. Point the frontend at the API. Replace the placeholder and upload over your course 1 page.

sed -i "s|REPLACE_WITH_PUBLIC_IP|$API_IP|" index.html
aws s3 cp index.html "s3://puff-frontend-$LOGIN/index.html" --content-type text/html

echo "http://puff-frontend-$LOGIN.s3-website-us-east-1.amazonaws.com"

Open that URL and post a message, then ask your neighbor to open your URL and post one too.
Congratulations, your cloud has its first tenant 🌻

✅

How you know it works: curl -s http://<public-ip>:8080/health prints {"status":"ok"}, curl -s http://<public-ip>:8080/api/messages returns a JSON list, and a message posted from http://puff-frontend-<yourlogin>.s3-website-us-east-1.amazonaws.com appears in the list within 5 seconds.

🧯 If it doesn't work
  • curl hangs: wait two minutes, then check puff-api-sg has the 8080 rule.
  • curl says "connection refused": the instance is up but the container isn't. Connect with EC2 > Instances > puff-api > Connect > EC2 Instance Connect and run sudo tail -50 /var/log/cloud-init-output.log, then sudo docker ps -a and sudo docker logs puff-api.
  • Container logs show a database timeout: puff-db-sg must allow 5432 from puff-api-sg.
  • "password authentication failed": DB_PASSWORD was regenerated after a terminal reset. Reset it with aws rds modify-db-instance --db-instance-identifier puff-db --master-user-password "$DB_PASSWORD" --apply-immediately, then rebuild user-data.sh and relaunch the instance.
  • "database puff does not exist": the console form's initial database name was left empty. Delete and recreate puff-db with it filled in.
  • The website shows "Cannot reach the API": you opened the bucket over https://, which blocks calls to an http:// API. Use the s3-website URL above. Also check API_IP in index.html with grep API_BASE index.html.
  • Terminal reset and your variables are gone: rerun export LOGIN=... and export DB_PASSWORD=<the one you wrote down>, then reread the IDs with aws ec2 describe-security-groups --filters Name=group-name,Values=puff-api-sg,puff-db-sg --query 'SecurityGroups[].[GroupName,GroupId]' --output text.
  • The public IP changed after a stop and start: recreate index.html and rerun step 7.

🕵️ What's wrong with this deploy?

🧭

No lab for this one, you look at what you built the way an attacker would, then the way the person woken up at 3 a.m. when it breaks would.

The board app works, now list at least five problems with it, and for each one, what could happen and which AWS piece would fix it.
Five minutes alone, then compare with your neighbor.

Look at who can reach what, where the secrets are, what happens when something dies, and how you'd know it broke.
Keep your list, because next courses tick it off one capability at a time.

💡 The list we'll fix
  • The API is reachable by anyone on port 8080, with no load balancer in front. Course 3.
  • The database sits in a subnet routed to the internet, only a security group protects it. Course 3.
  • SSH is open to 0.0.0.0/0 and depends on a shared key. Course 4.
  • The DB password is in plain text in user data, the boot log and the container environment. Course 4.
  • No HTTPS anywhere: messages and the API travel in clear text. Courses 3 and 5.
  • One instance in one AZ: if it dies, Puff is down until someone notices. Course 5.
  • The frontend calls a raw public IP that changes on every stop and start. Courses 3 and 5.
  • No monitoring, no alerts, no audit of who changed what. Course 4.
  • Single-AZ database and an untested restore. Multi-AZ isn't allowed here, so it goes in your project justification.
  • Everything was clicked or typed by hand, so nobody can rebuild it identically. Course 6.

🎲 Today's quiz

🤔 Think about it

  • Your API runs at 5% CPU most of the day and 80% for ten minutes every hour. Which instance family fits, and what would make you change your mind?
  • A nightly job processes 2 hours of data and can restart from its last saved point. Which pricing model would you pick, and what happens to your bill and your deadline if AWS takes the instance back halfway?
  • Why does the API connect to the database by its endpoint name rather than an IP, and what would break during a Multi-AZ failover if it didn't?
  • If you terminate puff-api and launch a new one with the same user data, what survives and what's lost? Why is that exactly what you want?
💡 Hints
  • Burstable instances earn credits during the quiet 50 minutes. Look at whether the credit balance ever hits zero.
  • Spot is built for work that can be interrupted. Think about the deadline: what if no spare machine is free for an hour?
  • RDS moves the endpoint name to the twin. An IP would keep pointing at the dead database.
  • The data is in RDS, the code is rebuilt from user data. Nothing on the instance is precious, which is exactly what Auto Scaling needs in course 5.
