Course 4 · Security, governance and monitoring

Badges, safe secrets and a smoke detector

Puff has a private network now, but the database password is still in plain text, and if the board app died at 3:00 nobody would know.

Today, Puff gets what every real cloud has: identity (who's allowed to do what), secrets kept out of sight, a log of every action, and alerts that warn you before your users complain.

This is one of the most interesting course, security and monitoring are what turn a demo into something people can trust with their data.

🎯 By the end of today

  • You can explain why humans log in through SSO and machines use roles, and spot an IAM policy that grants too much.
  • You can explain envelope encryption and KMS to a teammate in two minutes.
  • You can store a secret in SSM Parameter Store and have an EC2 instance read it at boot, with no password in its user data.
  • You can draw a multi-account layout for a company and say where SCPs, logs and backups live.
  • You can wire a CloudWatch alarm to an SNS email, fire it on purpose, and find your own actions in CloudTrail.

📖 Words you'll meet today
  • IAM (Identity and Access Management): the AWS service that decides who can do what.
  • Role: an identity with no password that a person or a program borrows for a while, with credentials that expire on their own.
  • SSO (Single Sign-On): one company login that opens every tool, including AWS.
  • Least privilege: give each person or machine exactly the access its job needs, nothing more.
  • KMS (Key Management Service): the AWS service that holds encryption keys. You never touch the key, you ask KMS to use it for you.
  • Secret: anything that grants access, like a password or an API token.
  • SSM Parameter Store: a place in AWS Systems Manager (SSM) to keep settings and secrets.
  • AWS Organizations: the tool that groups many AWS accounts under one roof.
  • SCP (Service Control Policy): a rule set by the organization that nobody inside an account can break.
  • CloudTrail: the AWS service that records every action in your account.
  • CloudWatch alarm: a watcher on one number, like errors per minute, that reacts when it crosses a limit.
  • SNS (Simple Notification Service): the AWS service that turns an alarm into an email, an SMS or a message.

🪪 IAM, one level deeper

Most cloud breaches start with a leaked key that still worked.

In first course, you met IAM (Identity and Access Management) as users, groups and policies, here's the version you'll meet at work.

An IAM user has long-lived credentials, a password for the console and access keys (AKIA...) for the CLI (command line interface).

  • Those keys never expire on their own.
  • They end up on laptops, in CI (continuous integration, the tools that build your code) variables and in public GitHub repos, where bots find them within minutes.

An IAM role has no credentials of its own.
Something it trusts (a person, an EC2 instance, a Lambda function, another account) assumes the role and gets temporary credentials from STS (Security Token Service).
They last from 15 minutes to a few hours, then they're worthless, like a visitor badge.

🔍 Want more? IAM user vs IAM role, side by side
IAM userIAM role
CredentialsA password and keys that last foreverTemporary, handed out by STS each time
Who uses itOne person or one script, foreverAnyone or anything the role trusts
If credentials leakThey work until someone notices and deletes themThey expire on their own, usually within the hour
Typical use todayEmergency access, old toolsEverything else

Humans sign in through SSO (Single Sign-On, one company login backed by the company directory) and land in a role, machines get a role attached (an instance profile for EC2, an execution role for Lambda).
Nobody should hold an access key that doesn't expire.

You've done this since course 1.
Run aws sts get-caller-identity in the sandbox terminal and look at the ARN (Amazon Resource Name, the unique ID of anything in AWS), it says assumed-role/voclabs/....
AWS Academy logs you in through a role and your terminal holds temporary credentials, and your Puff instance does the same through LabInstanceProfile, which wraps the role LabRole.

🔍 Want more? How an instance gets its credentials

Temporary credentials from STS come in three parts, an access key, a secret key and a session token.
An EC2 instance asks its metadata service (an address only the instance itself can reach) for them, and the SDK (the AWS library in your code) or the CLI refreshes them before they expire.
You never copy a key onto the machine.

Least privilege, before and after

Least privilege means a role gets the permissions its job needs and nothing more, like a cashier's badge that opens the till and not the vault.

This is the policy many people write for the Puff API on their first day, because it works:

{
  "Version": "2012-10-17",
  "Statement": [
    { "Effect": "Allow", "Action": "ssm:*", "Resource": "*" },
    { "Effect": "Allow", "Action": "kms:*", "Resource": "*" }
  ]
}

The * means everything.
If someone gets to run code on that instance, they can read and delete every parameter in the account, and decrypt anything KMS lets them touch.

This version does the same job for Puff:

{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": "ssm:GetParameter",
      "Resource": "arn:aws:ssm:us-east-1:123456789012:parameter/puff/db/*"
    },
    {
      "Effect": "Allow",
      "Action": "kms:Decrypt",
      "Resource": "*",
      "Condition": { "StringEquals": { "kms:ViaService": "ssm.us-east-1.amazonaws.com" } }
    }
  ]
}

It has one read action, limited to the /puff/db/ path, and decryption only works when the request comes through Parameter Store.
A hacked API machine can read the Puff database password (it needs it anyway) and nothing else.

⚠️

The sandbox's LabRole is much closer to the "before" policy than the "after" one, and IAM is read-only for you, so you can't tighten it. That's fine for a classroom.

In your project justification, write down which role you would create and what it would allow.

How AWS decides: explicit deny wins

Every time anyone calls AWS, it checks every policy that applies, in three steps:

  1. It starts from deny, if nothing allows the action it's refused (the "implicit deny").
  2. If any policy that applies says "Effect": "Deny" for this action, it's refused, and nothing can override that.
  3. Otherwise, if a policy allows it and every guardrail like an SCP allows it too, it goes through.

It's like a nightclub, you need your name on the guest list, but if you're on the banned list no guest list helps you.

💡

Use deny for guardrails ("nobody may ever do X") and allow for jobs ("this role needs Y").
If you mix the two, nobody can read the policy anymore.

🔍 Want more? Which policies get checked, with an example

Example: a developer has AdministratorAccess, and the company's SCP denies cloudtrail:StopLogging. The developer can do almost anything, but stopping the audit trail fails with AccessDenied, because the explicit deny in the SCP beats the allow in the admin policy.

For each call, AWS gathers the caller's identity policies, the resource's own policy (an S3 bucket policy, a KMS key policy), any SCP from the organization and any permission boundary (a cap an admin can put on a role). All of them go through those three steps together.

🛡️ Zero Trust, applied to Puff

Attackers get in eventually, so you want the damage to stop at the first door.

The old model puts a strong wall around the network and trusts everyone inside.
Attackers get in anyway (a phished laptop, a leaked VPN password), and then they're trusted too.

Zero Trust drops the idea that being on the network means anything, like an office where every door checks your badge, even the ones deep inside.
Puff already has some of this, and today's hands-on adds the rest.

🔍 Want more? Zero Trust, piece by piece in your Puff
  • Never trust the network, a request from a private subnet isn't safe because of where it came from.
  • Verify every request, each call proves who's making it and gets checked against policy.
  • Use short-lived credentials, whatever leaks should expire before it's useful.
  • Apply least privilege, so a verified identity only reaches what it needs.
PrincipleWhere it shows up in your Puff
Never trust the networkThe database lives in a private subnet and still requires a password, and puff-db-sg only lets in traffic from puff-api-sg, not from "anything in the VPC"
Verify every requestEvery AWS call is signed with the caller's credentials and checked by IAM, including the instance reading its own password
Short-lived credentialsThe instance gets fresh credentials from LabInstanceProfile, with no access key on disk
No permanent way inToday you remove SSH and port 22, and you reach the machine through Session Manager, which checks you with IAM and records the session
🏢

Real-world corner: at Alan, a health insurance company, engineers sign in to AWS through SSO and access is given to groups, never to individuals, so when someone leaves, every AWS access goes with their company account.


We also run several AWS accounts and copy backups to a separate one, so even someone with full control of production (the live system real customers use) can't delete the copies.

🔑 Federation and Amazon Cognito

Nobody wants a separate password for every tool, and you don't want to store your app users' passwords yourself.

Federation means AWS trusts someone else to say who you are, like a hotel that accepts your passport instead of issuing its own ID card.

  • Your company's login system (Google Workspace, Okta, Microsoft Entra ID) checks your password and MFA (multi-factor authentication, the code on your phone).
  • Then it hands AWS a signed note saying "this is Alice, she's in group platform".
  • AWS maps that group to a role and never sees her password.

That covers your employees.
For your customers, the people who sign up to your app, use Amazon Cognito, which has two pieces that people mix up:

🅰️

User pool

A user directory for your app: sign-up, sign-in, password reset, MFA, "log in with Google".

After login it gives back tokens (JWT, JSON Web Tokens, small signed ID cards) your backend can check. You never store or hash passwords yourself.

🅱️

Identity pool

Swaps a token (from a user pool or Google, for example) for temporary AWS credentials through STS.

Use it when the browser or mobile app talks to AWS directly, say to upload a photo to S3.

🔍 Want more? Cognito for the board app, SAML and OpenID Connect

Example: if the board app needed accounts, the frontend would send users to a Cognito login page and attach the returned token to each POST /api/messages, and the API would read the author from the verified token instead of trusting the JSON.

The "signed note" in federation follows a standard: SAML (Security Assertion Markup Language, older, XML) or OpenID Connect (newer, built on JWT). Both let the login system vouch for you with a signature AWS can verify, without ever sharing your password.

🔐 Encryption at rest and in transit

Data gets stolen in two places, on the wire while it travels and on the disk where it's stored, so you protect both.

In transit means the bytes moving across a network are encrypted, almost always with TLS (Transport Layer Security, the "S" in HTTPS), like a sealed envelope instead of a postcard.
Puff stays on plain HTTP because the sandbox has no domain to issue a certificate for, so say so in your project justification.

At rest means data on disk is encrypted, so a stolen disk or snapshot is unreadable.
On AWS it's mostly a checkbox backed by KMS, with one catch for databases.

🔍 Want more? Encryption at rest, service by service
ServiceAt rest
S3New files are encrypted by default, you can switch to your own KMS key
EBS (the disks of EC2)Per disk, or turn on "encryption by default" for the whole Region
RDSChosen when you create the database, can't be switched on later
Parameter StoreSecureString parameters are encrypted with a KMS key
⚠️

RDS encryption is decided on day one.
Turning it on later means a snapshot, an encrypted copy of it, a restore and a switch-over with downtime.

Default to encrypted for every database, even the "temporary" ones, temporary databases often become production.

🔍 Want more? TLS hop by hop

Browser to ALB (your Application Load Balancer) is HTTPS with a certificate from AWS Certificate Manager, ALB to API can be encrypted again if the rules require it, and API to PostgreSQL can use TLS too (sslmode=require).

🗝️ KMS and envelope encryption, plainly

If your encryption key sits in a config file, whoever reads the file can read your data.

AWS KMS (Key Management Service) keeps encryption keys inside tamper-proof hardware you never see, and the key never leaves KMS.
You ask KMS to use the key for you, and every request is checked by IAM and the key's own policy, then logged in CloudTrail.

KMS only encrypts small things directly (up to 4 KB), so for real data AWS uses envelope encryption:

  1. Your service asks KMS for a data key, and KMS returns it twice, once in plaintext and once encrypted under your KMS key.
  2. Your service encrypts the data locally with the plaintext data key (fast, any size), then throws that key away.
  3. It stores the encrypted data key right next to the encrypted data.
  4. To read the data later, it sends the encrypted data key to KMS, KMS checks permissions and returns the plaintext data key, then the service decrypts the data and throws the key away again.

It works like a building where every office has its own key and all the office keys sit in one safe at reception, and the receptionist (KMS) checks your badge and writes down every visit.

🔍 Want more? The three kinds of KMS keys
  • AWS owned keys are invisible to you.
  • AWS managed keys (aws/ssm, aws/rds, aws/ebs) are created for you per service, free, rotated automatically, but you can't edit their policy or share them with another account.
  • Customer managed keys are yours, you write the key policy, you can disable them, share them across accounts and schedule their deletion.

That last point matters for backups: if you want to copy encrypted snapshots into a separate backup account, you need a customer managed key, because the AWS managed one can't be used by another account.

🤫 Secrets management

A secret is anything that grants access, like a database password, an API token or a signing key.

These rules hold everywhere:

  • never in Git,
  • never in user data,
  • never in a container image,
  • readable only by the identity that needs it.

AWS gives you two places to keep them.
Secrets Manager is built for secrets and can change passwords for you on a schedule, SSM Parameter Store is a free place for settings that can also hold encrypted secrets.

🔍 Want more? Secrets Manager vs Parameter Store, side by side
Secrets ManagerSSM Parameter Store
Built forSecretsSettings, including secrets as SecureString
EncryptionAlways, with KMSSecureString with KMS, String in clear
Changes the password for you on a scheduleYes, built in for RDS and othersNo, you build it yourself
CostPaid per secret per month, plus API callsStandard parameters are free
Sharing with another accountYesNot for standard parameters
In our sandboxNot availableAvailable

We use Parameter Store today because Secrets Manager isn't in the sandbox.
In a real company, we'd put database credentials in Secrets Manager for the automatic password rotation alone (RDS can even manage its master password there for you), and keep plain settings (feature flags, addresses, the database hostname) in Parameter Store.

🏛️ Governance: many accounts, one organization

🏛️

No lab for this one: AWS Organizations isn't available in AWS Academy, so you'll design it on paper.

If everything lives in one account, one wrong command or one stolen password can reach everything.

An AWS account is the strongest wall AWS has, nothing in one account can touch another unless both sides open a door, like separate apartments.
So companies use one account per environment or per team, and a mistake in staging can't delete production.

AWS Organizations groups those accounts under one management account, and it gives you:

  • a single bill,
  • a tree of organizational units (OUs, folders of accounts),
  • service control policies (SCPs).

An SCP is a rule on an account or a whole OU.
It never grants anything, it sets the maximum anyone in those accounts can do, even the account's root user.
Same logic as the nightclub, an explicit deny in an SCP beats any allow inside the account.

🔍 Want more? Classic SCPs
  • Deny any action outside eu-central-1 and eu-west-3 (keep data in Europe).
  • Deny cloudtrail:StopLogging and cloudtrail:DeleteTrail (nobody erases the audit trail).
  • Deny leaving the organization.
  • Deny creating IAM users with access keys, so everyone goes through SSO.

The management account sits at the top, with folders of accounts (OUs) under it for Security, Infrastructure, Workloads (split into prod and non-prod) and Sandbox.
Every account sends its CloudTrail logs to a log archive account in Security, and production sends its backups to a separate backup account in Infrastructure.

🔍 Want more? Landing zones

A landing zone is the ready-made starting setup of that organization: the OU structure, a security account, a log archive account that collects CloudTrail from every account, SSO wired to the company directory, baseline SCPs, and a way to create a new account that follows the rules from its first minute.
AWS Control Tower builds one for you, many teams build theirs in Terraform.

✏️ Design exercise: the account layout for a 200-person startup (15 min)

You've joined a 200-person health startup as its first platform engineer.
About 60 engineers, one main product (web and mobile apps, an API, a PostgreSQL database with customer health data), a data team running analytics, everything in one AWS account today. The CTO asks you for a target layout.

On paper, draw:

  1. The OU tree and every account, with a one-line purpose for each.
  2. Where CloudTrail logs go, and who can read them.
  3. Where backups go, and why there.
  4. Which SSO groups exist and which accounts each one can reach, with what level of access.
  5. Two SCPs you'd apply on day one, and on which OU.

There's no single right answer, compare with your neighbour, then open the toggle.

🧭 One possible layout (open after you drew yours)
  • Management account: Organizations, billing and SSO only. Nobody deploys workloads here.
  • Security OU: a log archive account (organization CloudTrail, read by security only, deletion denied by SCP) and a security tooling account.
  • Infrastructure OU: a shared networking account, and a backup account that receives encrypted copies through a customer managed KMS key.
  • Workloads OU, split into Prod (production, data platform prod) and Non-prod (staging, dev).
  • Sandbox OU: one account per team for experiments, with a budget alert and a strict SCP.
  • SSO groups such as engineers (read-only on prod, write on non-prod), platform (admin on infrastructure accounts), data (data platform accounts), oncall (time-boxed admin access to prod for the person on duty).
  • SCPs on the root: region restriction to your EU Regions, deny stopping CloudTrail, deny leaving the organization.

🕵️ CloudTrail: who did what, when

When something changes and nobody remembers doing it, you want a recording.

CloudTrail records the calls made to AWS, like a security camera for your account, who called (user, role, instance), what action, on which resource, from which IP, when, and whether it worked.
Console clicks are API calls too, so they show up.

Event history keeps 90 days of management events (creating, changing, deleting resources) per Region, free, with nothing to set up, and that's what you'll use today.

Example: production's security group suddenly allows 0.0.0.0/0 on port 5432.
CloudTrail tells you it was AuthorizeSecurityGroupIngress, called by the role oncall assumed by a specific SSO user, at 14:32, from the office IP. Now you know who to talk to.

🔍 Want more? Trails and organization trails

A trail sends events to an S3 bucket for as long as you want, and can include data events (S3 file reads, Lambda runs), which are high volume and paid.
In an organization, one organization trail sends every account's events to the log archive account, where nobody in the workload accounts can touch them.

📈 CloudWatch: metrics, logs, alarms

You want to know the board app is down before the first angry message.

Metrics are numbers over time, grouped by service (AWS/EC2, AWS/ApplicationELB, AWS/RDS).
EC2 sends basic metrics every 5 minutes for free, and the ALB sends request counts, response times and error counts every minute.

An alarm watches one metric, like a smoke detector, and sits in one of three states, OK, ALARM or INSUFFICIENT_DATA (not enough numbers yet).
When the state changes it triggers an action, usually an SNS topic, which passes the message on to email, SMS or a chat tool.

The two ALB error metrics are easy to confuse, and it matters today.
A 5xx is an HTTP error code meaning the server side failed.

HTTPCode_Target_5XX_CountHTTPCode_ELB_5XX_Count
Who produced the 5xxYour Flask app answered with a 500The ALB itself, because it got no usable answer
Typical causeA bug, the database refusing connectionsContainer down, nothing listening, timeouts, no healthy target
What it tells youYour code is failingYour service is gone
💡

Alert on what users feel (errors, slowness, nothing answering) and look at causes (CPU, memory, disk) on a dashboard.
A CPU at 90% that serves every request in 50 ms is a healthy machine doing its job.

An alert that wakes someone up should mean users are hurting.

🔍 Want more? Logs and tuning an alarm

Logs are lines of text, stored in log groups.
Set a retention when you create one, by default logs are kept forever and you pay for all of it.
Docker's awslogs driver can ship your container's output there.

You choose the statistic (average, sum, max), the period (how long each measurement window lasts), how many periods in a row must break the threshold, and what missing data means (is silence good news or bad news?).
An alarm can also watch a math expression combining several metrics. Beyond email, SNS can call a Lambda function that posts to Slack, or a paging tool that phones whoever is on duty.

🏭

In a data center: identities live in Active Directory or LDAP, encryption keys in an HSM (a hardware safe), monitoring in tools like Nagios or Zabbix, and security logs in a SIEM.
IAM, KMS, CloudWatch and CloudTrail do the same jobs, already wired to every service.

💸 Budgets and cost alerts

💸

No lab for this one: billing, Budgets and Cost Explorer are closed in the AWS Academy sandbox.

A forgotten NAT gateway or a leaked key used to mine crypto breaks nothing, it just costs money until the invoice arrives a month later.

With AWS Budgets you set an amount (say 200 USD per month) and get an email when spend crosses 50%, 80% or 100% of it, or when the forecast says it will, like a low-fuel light.
You hear about it on day two instead of at the end of the month.

Every new account should get a budget alert before its first workload.
In a landing zone that's built into account creation, so nobody has to remember.

🔍 Want more? Budget options

You can budget on cost, on usage, or on Savings Plans coverage (a discount you get by committing to spend), and filter by service or tag.

🚒 Running it: from MCO to SRE

Building Puff takes a week. Running it is every day after that.
French IT calls this MCO (maintien en conditions opérationnelles): keeping a system working, safe and up to date. It's the number one constraint of any IT department.

Running a system is four jobs:

  • Watch. Alarms that mean "act now", and nothing else.
  • Respond. Someone on call, and a known path from the alert to the fix.
  • Repair and learn. Fix it, then write down what happened and change something so it doesn't come back.
  • Maintain. Patch, upgrade, rotate secrets, test that backups really restore.

There are two ways to organize it, one per platform:

Platform 2.0: ITILPlatform 3.0: DevOps and SRE
Who runs itA separate operations teamThe team that builds it ("you build it, you run it")
ChangesApproved in a change board meetingSmall, automated, reversible, many per day
The promiseAn SLA (Service Level Agreement) in a contractAn SLO (Service Level Objective) with an error budget
After an incidentFind who made the mistakeBlameless postmortem: why did the system let it happen?
Repetitive workTicketsCalled toil, and automated away on purpose
📖 Words for running things
  • On call: being the person who gets paged when an alarm fires, for a week at a time, then handing over.
  • Runbook: the page an alert links to. What it means, what to check first, how to fix the usual cause.
  • SLO and error budget: "99.9% of requests succeed this month". The 0.1% left is a budget: spend it on risky changes, stop changing when it's gone.
  • Postmortem: the write-up after an incident: timeline, cause, what we change.
  • Toil: manual, repetitive work that grows with the system and teaches nothing.
🏢

Real-world corner: how on-call works at Alan, a health insurance company.

  • Engineers are on call for the services their team builds. The infrastructure team has its own rotation for the platform underneath.
  • Every alert must be actionable. If the person paged can only acknowledge it and go back to sleep, the alert gets fixed or deleted. Noise comes back when nobody owns it, so cleaning it is recurring work, not a one-off.
  • We keep incidents (now) and maintenance (upgrades, toil, later) as separate tracks, so urgent work doesn't eat everything else.
  • After an incident we write a blameless postmortem. Who clicked doesn't matter. Why the system let them, does.
  • We restore production backups on purpose. A backup you never restored is a hope, not a backup.
  • Before adding people to on-call, we measure it: how many pages, at what hours, how many were real.

Key point: your project defense includes a tiny on-call shift. I break something in your Puff, and you have two minutes to find it with the tools from this session.

🧪 Hands-on: pick one Module 9 lab

This one is a course lab, pick one of the two:

  • "Module 9 guided lab: securing applications with Amazon Cognito" (FR: « Atelier guidé : sécurisation des applications à l'aide d'Amazon Cognito »)
  • "Module 9 guided lab: encrypting data at rest with AWS encryption options" (FR: « Atelier guidé : chiffrement des données au repos à l'aide des options de chiffrement AWS »)

You'll either build a web app whose sign-in is handled by Cognito, or encrypt data with a KMS key you create and decrypt it again.

🤔

If you've built a login system before and want to see how it's done without storing passwords, take Cognito.
If KMS and envelope encryption felt abstract an hour ago, take encryption, it's the one you'll use in every job and you can't create KMS keys in the sandbox.
If you're unsure, take encryption.

These labs run in their own temporary account with their own timer, so nothing you create there touches Puff.
The lab tells you what to click, this page tells you why.

👀 In the Cognito lab, look at this
  • The app never sees or stores a password hash, Cognito does. Find where the app receives a token after login.
  • Open a token at jwt.io (it's a lab, the token is short-lived) and look at the claims: who issued it, for which app, when it expires.
  • Spot which part is the user pool and whether an identity pool is involved. Ask yourself what AWS credentials the browser ends up with, if any.
👀 In the encryption lab, look at this
  • The KMS key has a key policy separate from IAM. Read it and check who can manage the key and who can use it.
  • When you encrypt, look at the size and content of the output. The encrypted data key travels with the data, that's envelope encryption.
  • If the lab lets you disable the key or remove a permission, try a decrypt afterwards. That failure is why KMS matters, take away access to the key and the data is unreadable everywhere at once.
✅

How you know it works: Cognito, you can sign up, sign in and see your user listed in the user pool in the console. Encryption, you have an encrypted file that is unreadable as is, and you can decrypt it back to the original content with your key.

🧪 Hands-on: Puff gets identity, secrets, audit and alerts

This part happens in the sandbox.
Your tenant, the board app, will read its database password from Parameter Store at boot (no password in user data), with no SSH and no port 22, and a CloudWatch alarm will email you through SNS puff-alerts when it breaks.
Then you find your own actions in CloudTrail.

Start the sandbox, wait for the green dot, open the browser terminal. Your Puff from course 3 (puff-vpc, puff-alb, puff-api in a private subnet, puff-db) must be running.
If a step fails, the 🧯 toggle at the end covers the usual problems.

  1. Create the alarm. Pick option A (recommended) or B.

Option A, the ALB returns 5xx. Since you'll break the board app by stopping its container, the errors come from the ALB itself, so you alarm on HTTPCode_ELB_5XX_Count (see the table in the CloudWatch section):

LB_DIM=$(aws elbv2 describe-load-balancers --names puff-alb \
  --query 'LoadBalancers[0].LoadBalancerArn' --output text | cut -d/ -f2-4)

aws cloudwatch put-metric-alarm --alarm-name puff-alb-5xx \
  --namespace AWS/ApplicationELB --metric-name HTTPCode_ELB_5XX_Count \
  --dimensions Name=LoadBalancer,Value=$LB_DIM \
  --statistic Sum --period 60 --evaluation-periods 1 \
  --threshold 5 --comparison-operator GreaterThanOrEqualToThreshold \
  --treat-missing-data notBreaching \
  --alarm-actions $TOPIC --ok-actions $TOPIC

Option B, CPU above 70% for 5 minutes on the API instance (basic monitoring sends one number every 5 minutes, hence the 300 s period):

aws cloudwatch put-metric-alarm --alarm-name puff-api-cpu \
  --namespace AWS/EC2 --metric-name CPUUtilization \
  --dimensions Name=InstanceId,Value=$NEW \
  --statistic Average --period 300 --evaluation-periods 1 \
  --threshold 70 --comparison-operator GreaterThanThreshold \
  --alarm-actions $TOPIC --ok-actions $TOPIC

Bonus: also create the same alarm as option A on HTTPCode_Target_5XX_Count, named puff-app-5xx. It fires when your code answers with errors.

Option A: in the Session Manager tab, stop the container:

🧯 If it doesn't work
  • Target never becomes healthy: open a Session Manager shell and run sudo cat /var/log/cloud-init-output.log. An AccessDenied on ssm:GetParameter means the instance profile is missing (check step 5), an empty password means a typo in the parameter name.
  • The container starts but every request fails with a 500: aws rds describe-db-instances --db-instance-identifier puff-db --query 'DBInstances[0].DBInstanceStatus' must say available, not modifying. Restart the container once it's available: sudo docker restart puff-api.
  • The instance doesn't appear in Session Manager: it needs outbound internet through your NAT gateway to reach Systems Manager. Check the private subnet's route table has 0.0.0.0/0 to the NAT gateway, and wait 2 to 3 minutes after boot.
  • No email: check spam, check the subscription isn't PendingConfirmation, and use aws cloudwatch set-alarm-state --alarm-name puff-alb-5xx --state-value ALARM --state-reason test to test the notification path without breaking anything.
  • Alarm stuck in INSUFFICIENT_DATA (option B): EC2 basic metrics arrive every 5 minutes, give it 10.
  • aws commands fail with an expired token: your sandbox session ran out. Restart the lab, reopen the terminal and re-run step 1.

🤔 Think about it

  • Your API reads the database password at boot and passes it to the container as an environment variable. Who can still see it, and what would you change so they can't?
  • An SCP denies s3:DeleteBucket on the Prod OU. A developer with AdministratorAccess in a prod account tries to delete a bucket. What happens, and why can't the account's admin fix it from inside the account?
  • You changed the password in Parameter Store and in RDS. What happened to the old Puff instance, and why did you replace it instead of fixing it?
  • Why does copying RDS snapshots into a separate backup account protect you against things that encryption alone doesn't?
  • Your CPU alarm fired at 3am because a nightly job pushed CPU to 75%, and nobody using the board app noticed anything. What would you change?
💡 Hints
  • Think about docker inspect, the process environment, and who can open a Session Manager shell. The app could call SSM itself with boto3 at startup.
  • Go back to the three steps of how AWS decides, and remember who controls SCPs.
  • User data runs once at first boot, so the container keeps the old password until it's replaced. In course 5, with an Auto Scaling group, replacing instances becomes routine.
  • Think about who holds the credentials to delete things in production, and about ransomware.
  • Symptoms versus causes: did users feel anything?
